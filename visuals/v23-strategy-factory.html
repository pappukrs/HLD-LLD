Strategy and Factory

The user picks a payment method at checkout. A factory turns the string 'upi' into a strategy object. The checkout service only calls strategy.pay() and never asks which method it is.

Runtime link: the strategy the context holds now Request / call Success Rejected

Say this in the interview

"Each payment method is a strategy behind one PaymentStrategy interface. A factory maps the request's method string to a strategy, and fails fast on unknown values. CheckoutService holds the interface and delegates, so adding pay-later is one new class plus one registry line, with no change to checkout."

The code

interface PaymentStrategy { pay(amount: number): Promise<Receipt>; }

class UpiStrategy implements PaymentStrategy {
  constructor(private psp: UpiPsp) {}
  async pay(amount: number) { return this.psp.collect(amount); }
}

const registry: Record<string, () => PaymentStrategy> = {
  card: () => new CardStrategy(gateway),
  upi: () => new UpiStrategy(psp),
  wallet: () => new WalletStrategy(walletRepo),
};

class PaymentFactory {
  static create(type: string): PaymentStrategy {
    const make = registry[type];
    if (!make) throw new UnsupportedMethodError(type);
    return make();
  }
}

class CheckoutService {
  constructor(private strategy: PaymentStrategy) {}
  setStrategy(s: PaymentStrategy) { this.strategy = s; }
  checkout(amount: number) { return this.strategy.pay(amount); }
}

Check yourself

Strategy vs State: they look the same in UML. What is different?
In Strategy the client chooses the object and it rarely changes during the call. In State the state objects themselves move the context to the next state.
Why a registry map instead of a switch inside the factory?
A map can be extended (even by plugins) without editing the factory. A switch in one factory is also acceptable: at least the switch lives in one place, not in every service.
Should strategies be singletons or new per request?
Stateless strategies can be shared (create once, reuse). If a strategy keeps per-request data, create a new one for each request so requests do not leak into each other.
Where does the unknown-method check belong?
At the boundary, in the factory or in request validation. Return 400 there, so the rest of the code can trust that the strategy exists.
