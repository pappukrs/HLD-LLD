Load Balancing Algorithms

A load balancer spreads requests over many servers and stops sending to the ones that are sick. The algorithm decides who gets the next request: in turn, the least busy, or always the same server for the same client.

Say this in the interview

"I'll put an L7 load balancer in front of stateless app servers. Least connections handles uneven request cost better than round robin. Health checks remove bad servers in seconds, and connection draining lets me deploy without dropping requests. I avoid sticky sessions by keeping session state in Redis; if I need affinity, I use consistent hashing so adding a server moves few clients."

L4 vs L7

  • L4 (TCP/UDP): routes by IP and port, very fast, cannot see the URL. Example: AWS NLB.
  • L7 (HTTP): can route by path, header or cookie, terminate TLS, retry, and rate limit. Example: ALB, Nginx, Envoy.
  • The LB itself must not be a single point of failure: run a pair (active-passive with a floating IP) or use a managed, multi-AZ one.

Check yourself

Why does round robin fail when some requests are slow?
It counts turns, not work. A server with three long reports still gets its turn, so its queue grows while others are idle. Least connections looks at in-flight work instead.
What is the difference between liveness and readiness checks?
Liveness asks "is the process alive?" (restart it if not). Readiness asks "can it take traffic now?" (DB connected, warm-up done). The LB should use readiness, so a starting server gets no traffic yet.
How do you deploy with zero dropped requests?
Mark the server as draining: the LB sends no new requests, waits for in-flight ones to finish (a deregistration delay, often 30 s), then removes it. Deploy, wait for readiness, add it back. Repeat one server at a time.
