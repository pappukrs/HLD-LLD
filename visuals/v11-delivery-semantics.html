Delivery Semantics and Idempotency

A consumer can crash between doing the work and sending the ack. Ack first and you may lose a message (at-most-once). Ack after and you may process it twice (at-least-once). An idempotency key turns "twice" into "once in effect".

Message Ack / commit DB write Lost / duplicate / crash

Say this in the interview

"The queue gives at-least-once delivery, so duplicates will happen. Every message carries an idempotency key, like the order id. The consumer inserts that key into a processed table with a unique constraint and applies the charge in the same DB transaction. A duplicate fails the insert, so we skip it and ack. That gives an exactly-once effect without needing exactly-once delivery."

Why exactly-once delivery is not on the menu

The ack can be lost on the network. Then the sender cannot know whether the work happened, so it must either retry (risk a duplicate) or give up (risk a loss). No protocol removes this choice.

Kafka's "exactly-once" covers read → process → write inside Kafka (idempotent producer + transactions). Side effects outside Kafka, like a card charge or an email, still need idempotency.

Check yourself

Is "UPDATE balance = balance − 100" idempotent?
No: running it twice subtracts 200. "SET status = 'PAID' WHERE id = 42" is idempotent: running it again changes nothing. Make non-idempotent writes safe with a dedupe key in the same transaction.
Why must the dedupe insert and the charge be in one transaction?
If you insert the key, then crash before the charge, the retry is skipped and the charge never happens. If you charge, then crash before the insert, the retry charges again. One transaction makes both happen or neither.
How long do you keep processed keys?
At least as long as a duplicate can still arrive: the broker retention plus the client retry window, often 24 hours to 7 days. Then delete them with a TTL or a cleanup job.
