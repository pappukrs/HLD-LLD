Seat Locking and Race Conditions

Node runs one thread, but every await lets another request run. Alice and Bob book seat A7 at the same moment. A plain check-then-act sells it twice. Then we fix it four ways.

Alice's request [A] Bob's request [B] Wrong result Dashed = reply

Say this in the interview

"Check-then-act across an await is a race, even in single-threaded Node. For one process, a per-seat mutex is enough. With many servers I make the database decide: a conditional update with a version, or SELECT … FOR UPDATE in a transaction. For the 10-minute hold while the user pays, I use Redis SET NX PX with a TTL, and the final booking is still a conditional write in the DB."

The bug and two fixes

// BUG: two requests can both see 'free'
async function book(seatId: string, userId: string) {
  const seat = await db.seat.find(seatId);           // await: other request runs
  if (seat.owner) throw new SeatTaken();
  await db.seat.update(seatId, { owner: userId });    // last write wins
}

// FIX: optimistic, let the DB check and write in one statement
const res = await db.query(
  `UPDATE seats SET owner = $1, version = version + 1
    WHERE id = $2 AND owner IS NULL AND version = $3`,
  [userId, seatId, seat.version]);
if (res.rowCount === 0) throw new SeatTaken();      // someone else won

// HOLD: Redis lock with TTL, released only by its owner
const ok = await redis.set(`hold:${seatId}`, userId, 'PX', 600_000, 'NX');
if (ok !== 'OK') throw new SeatHeld();

Check yourself

Node is single-threaded. How can there be a race?
JavaScript runs one callback at a time, but each await ends the current piece of work. Another request runs before yours resumes, so your earlier read may be stale.
How do you release a Redis hold safely?
Store the owner's id (or a random token) as the value. Release with a Lua script that deletes the key only if the value still matches, so you never delete someone else's newer hold.
Optimistic or pessimistic for a hot concert launch?
Under very high contention, optimistic causes retry storms. Use short holds (Redis or a holds table) plus a queue or waiting room in front, then a conditional final write.
