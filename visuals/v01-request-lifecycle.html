Life of a Request

One API call goes through DNS, a CDN edge, a load balancer, an app server, a cache and a database. Each hop costs time. Most of that time is network distance, not your code.

Setup (DNS, TLS) Network distance Server work Database

Say this in the interview

"The client resolves DNS, which points it to the nearest CDN edge. Static files are served from the edge. API calls go to our region, through an L7 load balancer to a stateless app tier. The app reads from Redis first and falls back to Postgres on a miss, then fills the cache with a TTL. Most latency is network round trips, so I keep connections warm, cache at the edge and keep the data path short."

Numbers worth remembering

  • Same data centre round trip: ~0.5 ms
  • Redis GET: ~0.5–1 ms including network
  • Indexed DB read: ~1–10 ms
  • Cross-continent round trip: 100–150 ms
  • New HTTPS connection: 1 RTT for TCP + 1 RTT for TLS 1.3

Check yourself

Why is the second request faster even before the cache hit?
The DNS answer is cached and the HTTPS connection is reused (keep-alive). That removes about 50 ms of setup before any server does work.
Why should the app tier be stateless?
Then the load balancer can send any request to any server. You can add, remove or replace servers freely. Sessions live in Redis or in a signed token, not in server memory.
A cache miss costs more than no cache at all. Why add one?
A miss adds ~1 ms, but a hit saves the DB call and protects the DB from load. With a 90% hit ratio the average and the DB load both drop a lot.
