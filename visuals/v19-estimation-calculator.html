Say this in the interview

"Let me size it. 150 million daily users post 2 times a day, so 300 million writes a day. That is about 3.5 thousand writes per second, 7 thousand at peak. With 100 reads per write, reads peak near 700 thousand per second, so reads must come from a cache. At 1 KB per post we add 300 GB a day, about 1.6 PB over 5 years with 3 replicas, so the data must be sharded."

Numbers to remember

  • 1 day ≈ 86,400 s ≈ 105 s. So 1M per day ≈ 12 per second, 1B per day ≈ 12K per second.
  • 1 year ≈ 365 days ≈ 3 × 107 s.
  • Powers of 1,000: KB → MB → GB → TB → PB. 1 B/s × 8 = bits per second.
  • Latency: memory ~100 ns, SSD random read ~100 µs, same-datacenter round trip ~0.5 ms, cross-continent ~100–150 ms.
  • Round hard: 86,400 → 100,000 is fine. Say that you are rounding.

Check yourself

10M writes a day. What is the average QPS?
10M ÷ 86,400 ≈ 116 per second. With the shortcut: 10M ÷ 105 = 100 per second.
Why size for peak and not the average?
Traffic follows the day and spikes on events. If you size for the average, the system fails exactly when most users are online. Peak is often 2–3× the average, and live events can be 10× or more.
Why is the cache number an upper bound?
The formula assumes every cached read is a different object. Real reads repeat (a hot tweet is read millions of times but stored once), so the true working set is usually smaller.
Is 1.6 PB too much for one database?
Yes. One machine holds a few TB to tens of TB. You need sharding over hundreds of nodes, or a store built for it (Cassandra, DynamoDB, S3 for media), and maybe tiering old data to cheaper storage.
