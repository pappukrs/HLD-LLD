Sharding Strategies

Sharding splits one big table across many databases so writes and storage scale. The shard key and the rule (range or hash) decide which queries stay on one shard, which shards get hot, and how much data moves when you add a shard.

New row / write Matched by query Hot / moved

Say this in the interview

"I'll shard by user_id with a hash, because most queries are per user and a hash spreads writes evenly. I won't shard by time, since all new writes would hit one shard. I'll create many logical partitions up front, say 1024, and map them to physical nodes, so adding a node moves whole partitions instead of rehashing everything. Hot keys get extra handling: caching, or splitting the key."

Choosing a shard key

  • High cardinality: many distinct values (user_id, not country).
  • Even traffic, not only even data: watch for celebrities and flash sales.
  • Matches the main query: "all orders of a user" should hit one shard.
  • Rarely changes: changing a row's key means moving the row.
  • Cross-shard joins and transactions are expensive: denormalise or use a saga.

Check yourself

Why is hash(key) % N bad for resharding?
When N changes, most keys get a new shard, so you copy most of the data. Use fixed logical partitions (many more than nodes) or consistent hashing, so only about 1/N of data moves.
A chat app shards messages by message_id. What breaks?
Loading one conversation needs all its messages, which are now spread over every shard. Shard by conversation_id instead, so one conversation lives on one shard. Order by a time-sortable message id inside it.
How do you handle one very hot key?
Cache it in front of the DB. For writes, split it: write to key#0..key#9 at random and sum on read (good for counters). Or give that tenant its own shard.
