SOLID Refactor

One PaymentService that does everything. We fix it one principle at a time and watch the class boxes change. The behaviour stays the same; the design gets easier to change and to test.

Changed in this step Smell / violation Fixed Dashed + triangle = implements

Say this in the interview

"I keep each class to one reason to change. The service depends on small interfaces like Payable and PaymentRepo, not on concrete classes. A new payment method is a new class, not an edit. I don't let a subclass throw 'not supported'; I split the interface instead. I inject dependencies through the constructor, so tests can pass fakes."

The final shape in TypeScript

interface Payable { pay(amount: number): Promise<Receipt>; }
interface Refundable { refund(paymentId: string): Promise<void>; }
interface PaymentRepo { save(p: Payment): Promise<void>; }
interface Notifier { send(to: string, msg: string): Promise<void>; }

class PaymentService {
  constructor(private repo: PaymentRepo, private notifier: Notifier) {}

  async pay(method: Payable, user: User, amount: number) {
    const receipt = await method.pay(amount);
    await this.repo.save({ userId: user.id, amount, receipt });
    await this.notifier.send(user.email, `Paid ${amount}`);
    return receipt;
  }
}

// composition root: the only place that knows concrete classes
const service = new PaymentService(new PostgresRepo(pool), new SmtpNotifier(cfg));

Check yourself

Does SRP mean one method per class?
No. It means one reason to change. A class can have many methods if they all change for the same actor, for example the payments team.
How do you spot an LSP violation in code review?
A subtype throws NotImplemented, does nothing on purpose, needs stronger input rules than the parent, or callers check instanceof before calling it.
What is the difference between DIP and DI?
DIP is the rule: high-level code depends on abstractions it owns. DI is one way to follow it: pass the dependency in (usually through the constructor) instead of creating it inside.
Should every class get an interface?
No. Add an interface when there is a second implementation or a test needs a fake. Extra interfaces with one implementation are just noise.
