Consistent Hashing

With hash(key) % N, changing N moves almost every key. Putting servers and keys on one ring means adding or removing a server moves only the keys next to it.

Server Key Key that moved

Say this in the interview

"I'll place servers on a hash ring and route each key clockwise to the next server. When a node joins or leaves, only about K/N keys move instead of nearly all of them. I'll use 100–200 virtual nodes per server so the load stays even, and weight them by capacity."

Where it's used

  • Partitioning in DynamoDB, Cassandra and Riak
  • Client-side sharding across Memcached or Redis nodes
  • Load balancers that need sticky routing (Maglev, Envoy ring hash)
  • Discord's message routing, Akamai's CDN

Modulo vs ring

hash % NRingRing + virtual nodes
Keys moved when 1 of N servers is added~ (N/(N+1)) of all keys~ 1/(N+1) of keys~ 1/(N+1), spread across all servers
Load balanceEvenUneven with few serversEven (more vnodes = smoother)
Lookup costO(1)O(log V) binary search on sorted positionsO(log V·N)
Heterogeneous serversNoNoYes: give bigger servers more vnodes

Check yourself

A server dies. Where do its keys go?
To the next server clockwise. With virtual nodes, its many small ranges go to many different servers, so no single neighbour gets flooded.
How do you add replication?
Store each key on the next R distinct physical servers clockwise (skip vnodes of the same server). This is Dynamo's "preference list".
Is there anything better for a fixed set of shards?
Jump consistent hash (Google) needs no ring memory and gives a perfect balance, but it only supports adding or removing servers at the end. Rendezvous (HRW) hashing is another option: pick the server with the highest hash(key, server).
