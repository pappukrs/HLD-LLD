Kafka Partitions and Consumer Groups

A Kafka topic is split into partitions: append-only logs. The message key picks the partition, so one key stays in order. In a consumer group each partition has exactly one reader, and each reader saves its position as a committed offset.

Say this in the interview

"I'll publish order events to a topic keyed by order_id, so all events of one order land in one partition and stay in order. Each downstream service is its own consumer group, so each one gets every event. Inside a group, partitions are the unit of parallelism, so I create more partitions than I expect consumers. Consumers commit offsets after processing, which gives at-least-once delivery, so the handlers are idempotent."

Rules to remember

  • Order is per partition, not per topic.
  • Max useful consumers in a group = number of partitions.
  • Adding partitions later changes hash(key) % N, so a key can move and lose ordering for a moment.
  • Reading does not delete. Messages stay for the retention time (e.g. 7 days) or forever with compaction.
  • A slow consumer only builds lag; it does not slow the producer.

Kafka vs a classic queue

Kafka (log)RabbitMQ / SQS (queue)
After a message is readIt stays; the consumer moves its offsetIt is acked and deleted
Many independent readersYes: one consumer group per serviceNeeds a fan-out exchange or SNS → many queues
Replay old messagesYes: reset the offsetNo (unless you archive them)
OrderingPer partitionPer queue (SQS FIFO: per message group)
Scaling consumersUp to the partition countAny number of competing consumers
Per-message routing, delays, prioritiesWeakStrong

Check yourself

A topic has 6 partitions and the group has 8 consumers. What happens?
6 consumers get one partition each and 2 stay idle. They are standbys: if a consumer dies, an idle one can take its partition at the next rebalance.
Commit before or after processing?
After processing gives at-least-once: a crash means some messages run again, so make handlers idempotent. Before processing gives at-most-once: a crash loses messages. Exactly-once needs Kafka transactions (read-process-write inside Kafka) or idempotent writes to the external system.
How do you keep a rebalance from stopping the whole group?
Use the cooperative sticky assignor, so only partitions that move are paused. Use static membership (group.instance.id) so a quick restart does not trigger a rebalance. Keep processing per poll short, below max.poll.interval.ms.
