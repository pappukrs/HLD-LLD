Bloom Filter

A tiny bit array that answers "is this item in the set?" with definitely not or maybe yes. It never gives a false "no", so you can skip slow lookups for items that are not there.

Works at any step. The hash is FNV-1a with 3 seeds, mod 24, so the same word always maps to the same bits. Add many words and watch the false-positive rate grow. Reset returns to the demo set.
Bit = 1 Bit being checked Bit = 0 (proves "not in set")

Say this in the interview

"I'll put a Bloom filter in front of the database. For an item that does not exist, the filter says 'no' and we skip the disk read. It can give false positives but never false negatives. For 1% false positives I need about 10 bits per item and 7 hash functions, so 1 billion items fit in about 1.2 GB of memory."

Where it's used

  • Cassandra, HBase, RocksDB: skip SSTables that cannot contain the key
  • Web crawler: "have I seen this URL already?"
  • Sign-up: fast "username is taken?" check before the DB
  • CDN: cache an object only on its 2nd request (skip one-hit wonders)
  • Redis: the BF.ADD / BF.EXISTS commands (RedisBloom)

Check yourself

Why can a Bloom filter never say "no" for an item you added?
Adding sets all k bits of the item to 1, and bits never go back to 0. So a later query finds all k bits set. A "no" needs at least one 0 bit.
The filter is full and false positives hit 20%. What do you do?
You cannot resize a Bloom filter in place. Build a bigger one from the source data, or use a scalable Bloom filter that adds a new, larger layer when the current one fills up.
What happens with more hash functions?
More hashes make each check stricter, but each insert also sets more bits, so the array fills faster. The best k is (m/n)·ln 2. Above that, false positives go up again.
Do you need k different hash functions?
No. The usual trick is double hashing: compute two hashes h1 and h2, then use h1 + i·h2 for i = 0…k−1. It gives the same accuracy with only two hash computations.
