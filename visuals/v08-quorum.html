Quorum Reads and Writes

In a leaderless store, each key lives on N replicas. A write succeeds when W replicas ack it; a read asks R replicas and keeps the newest version. If R + W > N, every read set overlaps every write set, so a read always sees the latest successful write.

Say this in the interview

"Each key is stored on N = 3 replicas. I use W = 2 and R = 2, so R + W > N and every read overlaps the last write; the coordinator returns the highest version and repairs stale replicas. With one node down, both reads and writes still succeed. For write-heavy keys I could pick W = 1, R = 3, but then a single lost node can lose acked writes. During bigger outages a sloppy quorum with hinted handoff keeps writes available, but it gives up the overlap guarantee."

What the overlap does not give you

  • Concurrent writes still conflict: you need versions (vector clocks) or last-write-wins.
  • A write that failed (fewer than W acks) may still sit on some replicas; it is not rolled back.
  • Sloppy quorums break the R + W > N guarantee until hints are handed off.
  • It is not linearizable on its own; that needs extra steps (e.g. read repair before returning).

Check yourself

N = 5. Which R and W give fresh reads and survive 2 nodes down?
W = 3 and R = 3. R + W = 6 > 5, and both need only 3 of 5 nodes, so up to 2 can be down.
Cassandra QUORUM vs LOCAL_QUORUM?
QUORUM counts replicas across all data centres, so it pays cross-region latency. LOCAL_QUORUM counts only the local DC: fast, and fresh within that DC, but another DC can be behind.
How do stale replicas get fixed?
Read repair: the coordinator writes the newest version back to stale replicas it read. Hinted handoff: a stand-in node replays writes when the owner returns. Anti-entropy: background Merkle-tree comparison finds and fixes the rest.
