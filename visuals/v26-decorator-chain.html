Decorator and Chain of Responsibility

Both patterns pass a call through a line of objects. A decorator wraps one object and always calls the inner one, adding behaviour around it. In a chain, each handler decides: handle it and stop, or call next().

Call going in Success Stopped / failed Same interface at every layer

Say this in the interview

"I keep EmailNotifier simple and add retry, logging and rate limiting as decorators that implement the same Notifier interface. I compose them at startup, and the order is a design choice. For request checks I use a chain: each middleware either responds and stops, or calls next()."

Both in TypeScript

interface Notifier { send(msg: Message): Promise<void>; }

class RetryNotifier implements Notifier {
  constructor(private inner: Notifier, private tries = 3) {}
  async send(msg: Message) {
    for (let i = 1; ; i++) {
      try { return await this.inner.send(msg); }
      catch (e) { if (i >= this.tries) throw e; await sleep(100 * 2 ** i); }
    }
  }
}

const notifier: Notifier =
  new RateLimitNotifier(new LoggingNotifier(new RetryNotifier(new EmailNotifier(smtp))), bucket);

// Chain of Responsibility: Express middleware
const auth: RequestHandler = (req, res, next) =>
  req.headers.authorization ? next() : res.status(401).end(); // no next(): chain stops

app.post('/orders', auth, validate(orderSchema), rateLimit, createOrder);

Check yourself

Retry inside or outside the rate limiter?
Rate limit outside retry means one token per user call. Retry outside the rate limiter means every attempt costs a token, which protects the provider better. Choose on purpose and say why.
Why not use inheritance: RetryingLoggingEmailNotifier?
Every combination would need its own subclass (class explosion). Decorators combine at runtime, and each one is tested alone.
In Express, what happens if a middleware neither responds nor calls next()?
The request hangs until the client or server times out. Every path must either send a response or call next() (or next(err)).
