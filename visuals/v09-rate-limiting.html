Rate Limiting Algorithms

A rate limiter decides, per user or API key, whether a request may pass now or gets 429 Too Many Requests. The algorithms differ in how they treat bursts, how smooth the output is, and how much memory they need.

Try it

Say this in the interview

"I'll use a token bucket per API key in Redis: capacity for bursts, refill rate for the average. The check and the decrement run in one Lua script so it is atomic across all gateway instances. Rejected calls get 429 with Retry-After. If Redis is down I fail open for normal endpoints and fail closed for expensive ones like login or OTP."

Where to put it

  • At the API gateway or edge, before any expensive work.
  • Key by user id or API key; by IP only for anonymous traffic (NAT puts many users behind one IP).
  • Several limits at once: per second (bursts) and per day (quota).
  • Return X-RateLimit-Remaining and Retry-After, so clients can back off.

Check yourself

Limit 100/min with a fixed window. What is the worst case?
100 requests at 0:59 and 100 more at 1:00. That is 200 requests in about one second, twice the intended rate.
Why not GET the counter, check it in Node, then SET it?
Two gateway instances can read the same value at once, and both let a request through. Use an atomic INCR with EXPIRE, or a Lua script that reads and updates in one step.
Token bucket or leaky bucket for a public API?
Token bucket: clients often send short bursts (page load) and should not wait. Leaky bucket fits when the downstream needs a steady rate, like sending to an SMS provider.
