State Pattern: Vending Machine

The machine behaves differently in each state. Instead of one big if (state === …) in every method, each state is a class that decides what an action does and which state comes next. Invalid actions are rejected by the state itself.

Machine log

    Say this in the interview

    "I model each state as a class that implements the same VendingState interface. The machine holds the current state and delegates every action to it. A state rejects actions that make no sense for it and moves the machine to the next state. Adding a SoldOut state is one new class, not a new branch in every method."

    The code

    interface VendingState {
  insertCoin(m: Machine, amount: number): void;
  selectItem(m: Machine, item: Item): void;
  cancel(m: Machine): void;
}

class IdleState implements VendingState {
  insertCoin(m: Machine, amount: number) {
    m.balance += amount;
    m.setState(new HasMoneyState());
  }
  selectItem() { throw new InvalidAction('Insert a coin first'); }
  cancel() { throw new InvalidAction('Nothing to refund'); }
}

class HasMoneyState implements VendingState {
  insertCoin(m: Machine, amount: number) { m.balance += amount; }
  selectItem(m: Machine, item: Item) {
    if (m.balance < item.price) throw new InvalidAction('Not enough money');
    m.setState(new DispensingState(item, m.balance - item.price));
  }
  cancel(m: Machine) { m.refund(m.balance); m.setState(new IdleState()); }
}

class Machine {
  balance = 0;
  private state: VendingState = new IdleState();
  setState(s: VendingState) { this.state = s; }
  insertCoin(a: number) { this.state.insertCoin(this, a); }
  selectItem(i: Item) { this.state.selectItem(this, i); }
  cancel() { this.state.cancel(this); }
}

    Check yourself

    Who changes the state: the machine or the state object?
    Usually the state object calls m.setState(next), because it knows the rules. The machine only delegates.
    Throw or return an error for an invalid action?
    Either works; be consistent. Throwing a typed InvalidAction keeps the API simple. Returning a Result is easier to test and to show in a UI.
    Two users press buttons at once on a server-side machine. Problem?
    Yes, if an action awaits I/O between reading and changing the state. Process actions for one machine one at a time, for example with a per-machine queue or lock.
    How would you add SoldOut?
    A SoldOutState that rejects coins and selections. DispensingState moves to it when stock reaches zero; a refill moves it back to Idle.
