Node.js Event Loop

One thread runs your JavaScript. Callbacks wait in queues and run only when the call stack is empty. Microtasks (process.nextTick first, then promises) run after every callback; then the loop moves through its phases. A long synchronous loop blocks all of it.

Running now / current phase Waiting callback (macrotask) Blocked

Say this in the interview

"Node runs JavaScript on one thread. After each callback it drains the nextTick queue, then the promise microtask queue. Then the loop moves through phases: timers, poll for I/O, check for setImmediate. Inside an I/O callback, setImmediate always runs before a 0 ms timeout. CPU-heavy work blocks every request, so I move it to worker_threads or split it into chunks."

The snippet and its output

import fs from 'node:fs';
const log = console.log;

fs.readFile(__filename, () => {           // runs in the poll phase
  log('sync 1');
  setTimeout(() => log('timeout'), 0);       // timers phase, next loop
  setImmediate(() => log('immediate'));      // check phase, this loop
  Promise.resolve().then(() => log('promise'));
  process.nextTick(() => log('tick'));
  log('sync 2');
});

// sync 1, sync 2, tick, promise, immediate, timeout

// Don't block the loop: yield between chunks
async function sumChunks(items: number[]) {
  let total = 0;
  for (let i = 0; i < items.length; i += 10_000) {
    for (const x of items.slice(i, i + 10_000)) total += x;
    await new Promise<void>((r) => setImmediate(r)); // let I/O run
  }
  return total;
}

Check yourself

At the top level of a script, which prints first: setTimeout(0) or setImmediate?
It is not fixed. It depends on whether 1 ms has passed when the loop starts. Inside an I/O callback, setImmediate always wins, because check comes right after poll.
Does nextTick always run before promises?
In CommonJS and inside callbacks, yes. At the top level of an ES module, the module itself runs as a microtask, so promise callbacks queued there can run before nextTick ones.
Are microtasks drained between two setTimeout callbacks?
Yes, since Node 11. A promise resolved inside the first timer runs before the second timer.
Does fs.readFile block the event loop?
No. It runs in the libuv thread pool (4 threads by default) and its callback is queued for the poll phase. fs.readFileSync does block.
