Saga and Transactional Outbox

One order touches three services, and each one has its own database. A saga runs one local transaction per service and undoes the earlier steps if a later one fails. The outbox makes sure "save the data" and "publish the event" never drift apart.

Say this in the interview

"Order, payment and inventory each own their data, so I can't use one ACID transaction. I'll use an orchestrated saga: each step is a local transaction with a compensating action, run in reverse on failure. Every service writes its event to an outbox table in the same transaction as its data, and a relay or CDC publishes it to Kafka. Delivery is at-least-once, so every handler is idempotent."

Rules for good compensations

  • A compensation is a new action ("refund", "release"), not a rollback. The original write stays in history.
  • It must be idempotent and retried until it succeeds. A compensation that can fail for good needs a human or a reconciliation job.
  • Put steps that cannot be undone (send email, ship parcel) last, after the risky steps.
  • Sagas have no isolation. Use states like PENDING or a reservation so other requests don't act on half-done data.

Check yourself

Why not publish to Kafka first, then write the DB?
Same bug in reverse: if the DB write fails after publishing, consumers act on an order that does not exist. Any two separate writes can half-fail. The outbox turns them into one local write.
The orchestrator crashes in the middle of a saga. What happens?
It stores the saga state (current step, status) in its own DB after every step. On restart it reads that state and continues forward or continues compensating. Because steps are idempotent, repeating the last one is safe.
Polling the outbox vs CDC?
Polling (SELECT unsent rows every 100 ms) is simple but adds DB load and some delay. CDC (Debezium reads the Postgres WAL or MySQL binlog) has low delay and no extra queries, but it is one more system to run.
How does a consumer skip duplicate events?
In the same transaction as its own change, it inserts the event ID into a processed_events (inbox) table with a unique key. A duplicate hits the unique key, so the handler skips it.
