# SD Day 12 — Idempotency + Distributed Transactions (Outbox, Sagas)

*(~1 hr · the direct sequel to Day 11. Yesterday's punchline was "messages arrive at-least-once, so make consumers idempotent." Today is *how* — plus the bigger problem: when one business action touches **several services/databases**, there's no single transaction to wrap it in, so how do you stay correct? This is YOUR payments domain — you've effectively built this; today names it so you can defend it in an interview. Sits on Day 11 (queues) + Day 10 (consistency); core senior material.)*

---

## 1. The two problems, stated plainly

1. **Duplicates.** Networks retry. A client resends, a queue redelivers, a webhook fires twice. If
   "charge ₹500" runs twice, you double-charge. → fix with **idempotency**.
2. **Partial failure across services.** "Place order" = reserve inventory **+** charge card **+** create
   shipment, each in a *different* service/DB. A normal DB transaction can't span them. If the card
   charge succeeds but shipment creation crashes, you're in a broken half-done state. → fix with
   **saga** (and reliably emit the events with the **outbox** pattern).

> **One line:** *Idempotency makes "do it twice" safe; sagas make "do five things across five
> services, some of which may fail" recoverable.*

---

## 2. Idempotency — "doing it twice = doing it once"

**Definition:** an operation is **idempotent** if performing it multiple times has the **same effect
as performing it once.** `GET`, `PUT x=5`, `DELETE` are naturally idempotent. `POST "add ₹500"` /
"increment" / "append" are **not** — that's where the danger is.

The standard fix: the **idempotency key.**

```
client generates a unique key (UUID) for the operation
   POST /charge   Idempotency-Key: 7f3a-...    amount=500
server:
   seen this key before?
     ├── NO  → do the work, store (key → result), return result
     └── YES → skip the work, return the SAME stored result
```

So a retry with the **same key** returns the original result instead of charging again. (This is
exactly how Stripe's API works — and what you built into your payment webhooks.)

Implementation notes:
- Store keys in a fast store (Redis/DB) with a **TTL** (e.g. 24h) — long enough to cover all retries.
- The "check + insert" must be **atomic** (e.g. a unique constraint on the key column, or
  `SET key NX` in Redis) — otherwise two simultaneous retries both see "not seen" and both run.
- Key must be **generated by the client / caller per logical operation**, not per network attempt —
  all retries of the *same* intent share one key.

**Hook:** *"Give every operation a fingerprint; if you've seen the fingerprint, replay the answer
instead of redoing the work."*

---

## 3. Why distributed transactions are hard (no magic ACID across services)

In a single database, ACID gives you all-or-nothing: `BEGIN … COMMIT`, and a crash rolls everything
back. Across **microservices with separate databases**, that guarantee is gone — there's no shared
transaction.

The textbook answer is **2-phase commit (2PC)**: a coordinator asks every service "can you commit?"
then "commit!". It gives strong consistency but is **avoided in practice** because:
- It **blocks** — everyone holds locks waiting for the slowest participant.
- If the **coordinator dies** mid-protocol, participants are stuck holding locks (in-doubt).
- It scales badly and kills availability (it's a CP-heavy choice — Day 9).

So real systems give up on global ACID and instead accept **eventual consistency with
compensation** → the **saga pattern**.

---

## 4. Saga — break one big transaction into local steps + undo steps

> **A saga is a sequence of local transactions, one per service. Each step has a matching
> *compensating action* that undoes it. If any step fails, you run the compensations for the steps
> already done — "semantic rollback" instead of a real one.**

Order example (each line is one service's local commit):

```
 forward steps              compensation (undo) if a later step fails
 1. reserve inventory   ←→  release inventory
 2. charge card         ←→  refund card
 3. create shipment     ←→  cancel shipment
```

If step 3 fails: run "refund card", then "release inventory", in reverse. The system ends up in a
consistent state — not by rolling back a transaction, but by **actively compensating**.

Two ways to coordinate a saga:

- **Choreography (event-driven, no central brain):** each service emits an event; the next service
  listens and reacts. "OrderCreated → InventoryReserved → PaymentCharged → ShipmentCreated."
  Simple, decoupled, but the flow is **implicit** — hard to see the whole story or debug.
- **Orchestration (a central coordinator):** an *orchestrator* service explicitly tells each service
  what to do next and triggers compensations on failure. Easier to **understand, monitor, and change**;
  the orchestrator is one more thing to build. **Preferred for complex flows like payments.**

**Key caveat:** compensations aren't always clean — you can't un-send an email. You compensate with a
*new* action ("send a correction/apology" or "issue a refund"), not by pretending it never happened.
And saga steps are **eventually consistent** — there's a window where inventory is reserved but
payment not yet charged. Design for it.

**Hook:** *"No undo button across services — so write your own undo for every step, and run them
backwards when something breaks."*

---

## 5. The outbox pattern — the "two writes" problem, solved

Here's the subtle bug that bites every event-driven system. A service must do **two** things when
something happens:

1. write to its **own database** ("order saved"), and
2. **publish an event** to the queue ("OrderCreated") so others react.

These are **two separate systems** (DB + Kafka/RabbitMQ). You **cannot** make them atomic:

```
 save order to DB ✔
 ...crash before publish...        → DB has the order, but NO event ever sent. Others never know. ✗

   or:

 publish event ✔
 ...crash before DB commit...      → event says "order created" but DB has no order. Phantom. ✗
```

**The outbox pattern fixes it:** instead of publishing directly, write the event **into an `outbox`
table in the same database transaction** as your business data. Now it's **one atomic local commit** —
either both the order and its pending event are saved, or neither is.

```
┌─ single DB transaction ─────────────┐
│  INSERT into orders   (...)          │
│  INSERT into outbox   (OrderCreated) │   ← both commit together, atomically
└──────────────────────────────────────┘
        ▼ (separately, after commit)
  a relay / CDC process reads new outbox rows → publishes to Kafka → marks them sent
```

A separate **relay** (a poller, or Change-Data-Capture like Debezium tailing the DB log) reads
unsent outbox rows and publishes them to the broker, marking each sent. If the relay crashes after
publishing but before marking sent, it re-publishes → **at-least-once** → which is exactly why
**consumers must be idempotent** (§2). It all ties together.

**Hook:** *"Don't write to the DB and the queue separately — write the event into the DB with the
data, then let a relay ship it. One commit, no lost or phantom events."*

---

## 6. How it all clicks together (the loop)

```
outbox guarantees the event is RELIABLY emitted (at-least-once)
        ↓
the saga uses those events to drive multi-service steps + compensations
        ↓
at-least-once means duplicates happen
        ↓
idempotency keys make duplicate handling harmless
        ↓
net result: correct, eventually-consistent business workflow across services
```

That's the senior story end-to-end: **outbox (reliable emit) + saga (coordinate + compensate) +
idempotency (tolerate duplicates) = distributed correctness without 2PC.**

## 7. Map it to YOUR systems (interview gold)

- **Payment orchestration (your fintech work):** this is the whole chapter. Idempotency keys on
  charge endpoints (no double-charge on webhook retries), an **orchestration saga** across
  payment/ledger/notification services with **refund as the compensation**, and the **outbox** so a
  "PaymentSucceeded" event is never lost between your DB and RabbitMQ. Your **reconciliation** job is
  the safety net that catches any saga that ended in a half state.
- **Webhook reliability:** providers retry webhooks → you **must** dedupe by event id (idempotency) or
  you process the same payment event multiple times.
- **Order/booking flows:** reserve → pay → confirm as a saga with releases/refunds as compensations.

> The interview line: *"I don't use 2-phase commit across services — it blocks and doesn't scale. I
> use the **outbox pattern** to emit events atomically with the DB write, a **saga** (usually
> orchestrated) to sequence the steps with **compensating actions** for rollback, and **idempotency
> keys** so at-least-once delivery can't double-apply anything. Reconciliation catches the rest."*

---

## 8. The traps that catch people

1. **Reaching for 2PC.** Almost always the wrong answer in microservices — say *why* (blocking,
   coordinator failure, poor availability) and pivot to saga.
2. **"We'll just publish the event after saving."** That's the two-writes bug (§5). Without an outbox,
   a crash loses or phantoms events. Interviewers probe exactly here.
3. **Idempotency key per *attempt* instead of per *intent*.** If each retry makes a new key, dedup
   never triggers. One logical operation = one key across all its retries.
4. **Forgetting compensations can fail too / aren't perfect.** They're *semantic* undo (refund, not
   "un-charge"), and the relay/compensator itself needs retries + idempotency.
5. **Assuming sagas are strongly consistent.** They're **eventually** consistent — there's a visible
   in-between state. That's the trade for availability.

## 9. The whole day on one page (say it out loud)

> *"Two problems: duplicates and partial failure across services. Duplicates I solve with
> **idempotency** — a client-supplied key per operation; if I've seen the key I replay the stored
> result instead of redoing the work, so retries can't double-charge. Partial failure I solve with a
> **saga**, not 2-phase commit (which blocks and fails badly): I break the workflow into one local
> transaction per service, each with a **compensating action**, and on failure I run the compensations
> backwards — eventual consistency with semantic rollback. To emit the driving events reliably I use
> the **outbox pattern**: write the event into an outbox table in the *same* DB transaction as the
> business data, then a relay/CDC ships it to the broker — one atomic commit, no lost or phantom
> events. That emit is at-least-once, which is exactly why consumers stay idempotent. Outbox + saga +
> idempotency = correctness across services without distributed transactions."*
