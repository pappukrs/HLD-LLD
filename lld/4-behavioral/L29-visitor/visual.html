Visitor: new operations on a fixed tree

The file and folder classes never change. Each new operation (size, search, export) is a visitor that walks the tree. Two calls, node.accept(v) then v.visitFile(this), pick the code by both the node type and the operation.

    Say this in the interview

    "Node types here are stable, file and folder, but operations keep growing, so I'd use a Visitor. Each node's accept(v) calls back v.visitFile(this) or v.visitFolder(this). That's double dispatch: the code depends on both the node type and the operation. A new operation is one new class. The cost is that a new node type touches every visitor. In TS with plain data I'd use a discriminated union plus an exhaustive switch instead."

    The code (highlights follow the steps)

    Check yourself

    What is double dispatch?
    Picking code by two runtime types. node.accept(v) picks by node type, then v.visitFile(this) picks by visitor type.
    You add SymlinkNode. What breaks?
    The visitor interface gets visitSymlink, and every visitor must implement it. The compiler lists each one.
    You add "count files". What changes?
    One new CountVisitor class. Zero node edits.
    Why not if (n instanceof FileNode) in one function?
    A new type silently falls through to the default. The visitor interface (or assertNever) makes the compiler catch it.
