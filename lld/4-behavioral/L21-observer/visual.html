Observer and pub-sub: announce, don't call

With Observer, the subject keeps a list and calls each observer itself. With pub-sub, a broker sits in the middle and routes by topic, so publishers and subscribers never know each other. Both can block the caller if you call handlers one by one, and a broker adds buffering for offline subscribers plus duplicate deliveries you must handle.

Say this in the interview

"Inside one service I use Observer: the order service emits OrderPlaced and listeners subscribe. I don't let a slow listener delay the response, so I start them without awaiting and isolate their errors. Across services I use a broker with topics, so publishers don't know subscribers and messages survive a subscriber being down."

Sync vs async notify

interface Observer<E> { update(e: E): Promise<void>; }

class Subject<E> {
  private observers = new Set<Observer<E>>();
  subscribe(o: Observer<E>) {
    this.observers.add(o);
    return () => this.observers.delete(o); // unsubscribe
  }

  // sync: caller waits for every observer; one throw stops the rest
  async notifySync(e: E) {
    for (const o of this.observers) await o.update(e);
  }

  // async: start all, return now, isolate failures
  notify(e: E) {
    const all = [...this.observers].map((o) => o.update(e));
    void Promise.allSettled(all).then(logRejected);
  }
}

Observer vs pub-sub

Observer (in-process)Pub-sub with a broker
Who knows whomSubject holds direct references to observersBoth sides know only the broker and a topic name
FilteringEvery observer gets every event (or one subject per event type)By topic, sometimes by key or attributes
Subscriber is down or slowEvent is lost or the caller waitsBroker buffers; subscriber catches up later
DeliveryFunction call, same processNetwork, at-least-once, so handlers must be idempotent
Node examplesEventEmitter, RxJS SubjectRedis pub/sub (no buffer), Kafka, SNS + SQS, RabbitMQ

Check yourself

Does Node's EventEmitter.emit() wait for async listeners?
No. emit() calls each listener synchronously, in order. If a listener is async, emit gets back a promise and ignores it. A rejected promise there is unhandled unless you use captureRejections or catch it yourself.
Why does a forgotten unsubscribe cause a memory leak?
The subject keeps a reference to the observer, so the observer (and everything it holds) can never be garbage collected. Return an unsubscribe function and call it on shutdown or unmount.
Is Redis pub/sub a durable queue?
No. A subscriber that is offline misses the message. Use Redis Streams, Kafka or SQS when every message must be processed.
The broker delivers the same event twice. What stops a second email?
An idempotent consumer: it records processed event ids (a DB unique key, or Redis SET NX with a TTL) and skips ids it has seen.
