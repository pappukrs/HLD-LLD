Strategy: swap the algorithm, keep the caller

The user picks a payment method at checkout. Instead of a growing switch, each method is a strategy behind one interface. A factory turns the string 'upi' into a strategy object, and the checkout service only calls strategy.pay().

Runtime link: the strategy the context holds now Request / call Success Rejected / edited

The code

interface PaymentStrategy { pay(amount: number): Promise<Receipt>; }

class UpiStrategy implements PaymentStrategy {
  constructor(private psp: UpiPsp) {}
  async pay(amount: number) { return this.psp.collect(amount); }
}

const registry: Record<string, () => PaymentStrategy> = {
  card:   () => new CardStrategy(gateway),
  upi:    () => new UpiStrategy(psp),
  wallet: () => new WalletStrategy(walletRepo),
};

class PaymentFactory {
  static create(type: string): PaymentStrategy {
    const make = registry[type];
    if (!make) throw new UnsupportedMethodError(type); // 400
    return make();
  }
}

class CheckoutService {
  constructor(private strategy: PaymentStrategy) {}
  setStrategy(s: PaymentStrategy) { this.strategy = s; }
  checkout(amount: number) { return this.strategy.pay(amount); }
}

Try it: send a checkout request

Say this in the interview

"Each payment method is a strategy behind one PaymentStrategy interface. A factory maps the request's method string to a strategy and fails fast on unknown values with a 400. CheckoutService holds the interface and delegates, so adding pay-later is one new class plus one registry line, with no change to checkout. That is open/closed."

Check yourself

Strategy vs State: they look the same in UML. What is different?
In Strategy the client chooses the object and it rarely changes during the call. In State the state objects themselves move the context to the next state as events arrive.
Why a registry map instead of a switch inside the factory?
A map can be extended (even by plugins) without editing the factory. A switch in one factory is also acceptable: at least it lives in one place, not in every service.
Should strategies be singletons or new per request?
Stateless strategies can be shared. If a strategy keeps per-request data, create a new one for each request so requests do not leak into each other.
When is a function enough?
One method, no state, no dependencies beyond a closure: type PricingFn = (minutes: number) => number.
