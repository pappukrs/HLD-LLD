Mediator: the elevator dispatcher

Buttons, cars and the display never call each other. Each one only knows the dispatcher. The dispatcher holds the rule for who does what, so N objects need N links instead of N x (N-1) / 2.

Be the building

Press buttons on different floors, then tick to move cars. Put car C into maintenance or swap the strategy. Only the dispatcher's rule changes; buttons and cars stay the same.

Dispatcher log

    Say this in the interview

    "Floor buttons and cars don't talk to each other. They report to an ElevatorDispatcher, a mediator. It picks a car with a pluggable strategy and updates displays when a car arrives. Car movement stays in ElevatorCar, the rule stays in the strategy, and the dispatcher only routes, so it does not become a god class."

    The code (highlights follow the steps)

    class ElevatorDispatcher implements Dispatcher {  constructor(private display: Display, private pick: PickStrategy) {}  requestPickup(floor: number, dir: Direction) {    const car = this.pick(this.cars, floor);    car.addStop(floor);  }  carArrived(car: ElevatorCar, floor: number) {    this.display.show(car.id, floor);  }}class FloorButton {  press(dir) { this.dispatcher.requestPickup(this.floor, dir); }}

    Check yourself

    Chat room: A blocks B. Where does that rule live?
    In the room (the mediator). It checks A's block list before delivering B's message. Users have no references to each other.
    10 components: links with and without a mediator?
    Mesh: up to 45. Mediator: 10.
    How do you keep the mediator from becoming a god class?
    State and behaviour stay in colleagues, decisions go into a strategy, and the mediator only routes. Split it per workflow if it grows.
    How do you test ElevatorCar alone?
    Give it a fake Dispatcher that records calls. The car depends only on the interface.
