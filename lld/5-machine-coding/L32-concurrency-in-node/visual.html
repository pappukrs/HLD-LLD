Concurrency in Node: one seat, two users

Node runs one callback at a time, but every await lets another request run. Watch "check, await, act" sell a seat twice, then fix it: no gap, a mutex, a row lock, a version check, a Redis hold, and an idempotency key.

Say this in the interview

"Check-then-act across an await is a race, even in single-threaded Node. In one process I remove the gap or use a per-seat mutex. With many instances I make the database decide: a conditional update with a version, or SELECT … FOR UPDATE for a short transaction. The 10-minute hold while paying is Redis SET NX PX, and a unique constraint on (show, seat) is the last safety net. Payment retries carry an idempotency key."

Check yourself

Node is single-threaded. How can there be a race?
Each await ends the current piece of work. Another request runs before yours resumes, so your earlier read can be stale.
Why does the mutex fail with 2 pods?
Each process has its own Map of mutexes. Both pods grant the lock. Only a shared store (DB, Redis) can serialise across processes.
How do you release a Redis hold safely?
Store a token as the value and delete with a Lua script only if the value still matches, so you never delete someone else's newer hold.
Optimistic or pessimistic for a hot concert launch?
Optimistic causes retry storms there. Use short holds plus a queue or waiting room in front, then a conditional final write.
