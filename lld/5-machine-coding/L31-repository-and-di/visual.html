Repository and dependency injection

A wallet service that builds its own DB pool and reads the real clock cannot be tested or changed. Pull the dependencies out, put storage behind an interface, and let one composition root wire them. Then swap storage live and watch the service not change.

Say this in the interview

"Storage goes through a repository per aggregate. Today it's an in-memory map that returns copies; later it's Postgres with the same interface. The service gets its repositories, clock and id generator through the constructor, and main.ts is the only place that knows concrete classes."

"Save is a conditional update on a version column, so a racing write fails and retries instead of losing money."

Check yourself

Why must the in-memory repo return copies?
So a caller cannot change stored state without calling save. A real DB read returns a fresh object, so the fake must behave the same or tests lie.
Where should new PgWalletRepo() appear?
Only in the composition root (main.ts or a Nest module). Never in a service.
How does Nest inject an interface?
It cannot by type, because interfaces are erased. Bind a token: { provide: WALLET_REPO, useClass: PgWalletRepo } and @Inject(WALLET_REPO).
Two requests read v3 and both save. What happens?
The first save moves the row to v4. The second save says "I am based on v3", the check fails, it throws a conflict, and the caller reloads and retries.
