Adapter

Three payment SDKs, three shapes: one returns a promise and wants rupees, one uses callbacks and numeric error codes, one never throws and hides failure in a status field. Each adapter translates names, units and errors so the service sees one interface.

Say this in the interview

"The service depends on my PaymentProvider interface, not on any SDK. Each provider gets one adapter that converts the request, the units (paise vs rupees), the response and the error codes into my types. Adding or replacing a provider is one new class, and the domain code and tests don't change. Because every adapter has the same interface, a fallback router is easy: try A, then B."

Check yourself

Gateway A uses rupees as strings, B uses integer paise. Where do you convert?
Inside each adapter. The domain uses one unit everywhere (integer paise), so no money math happens in floats outside the edge.
The SDK throws { code: 'CARD_DECLINED' }. What should your adapter throw?
Your own error type, for example PaymentDeclinedError('CARD_DECLINED'), so the service never checks provider-specific codes and can treat all providers the same.
Object adapter vs class adapter?
An object adapter holds the adaptee as a field (composition). A class adapter extends it (inheritance). In TS use the object adapter: it works with any instance, and you cannot extend two classes anyway.
How do you test adapters?
A shared contract test suite that runs against every PaymentProvider implementation with the SDK stubbed, plus a few integration tests against each provider's sandbox.
