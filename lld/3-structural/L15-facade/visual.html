Facade: one door in front of many rooms

Three callers each wire up five subsystems, and one of them forgets the rollback. A facade writes the checkout flow once: right order, one try/catch, side effects off the hot path. Callers make one call.

The facade (lines light up with the steps)

async checkout(userId, items, coupon) {  const hold = this.inventory.reserve(items);  try {    const total = this.pricing.total(items, coupon);    const txn = await this.payments.charge(userId, total);    const order = this.orders.create(userId, total, txn);    this.inventory.commit(hold);    void this.notifier.send(userId, '...').catch(log);    return order;  } catch (e) {    this.inventory.release(hold);   // compensation    throw e;  }}

Say this in the interview

"CheckoutService is a facade over inventory, pricing, payments, orders and notifications. It owns the order of steps and the compensation: if payment fails, it releases the reserved stock. Every caller uses this one method, so the flow is written once. The subsystems keep their own rules, and I keep one facade per use case so it never becomes a god class."

Check yourself

Does a subsystem ever call back into the facade?
No. Arrows go one way: callers to facade, facade to subsystems. If the parts talk to each other through a central object that they know about, that is a Mediator.
Why is the email sent without await?
The order is already paid. A slow or failing SMTP server must not slow down or fail it. Start the send, catch and log errors, or publish an event for a worker.
Is it still OK to call Pricing directly?
Yes. A facade is a shortcut for the common flow, not a wall. A report job can use Pricing on its own.
What changes when the steps are separate services?
No local try/catch rollback. The facade becomes a saga orchestrator with persisted state, retries, idempotency keys and a compensating action per step.
