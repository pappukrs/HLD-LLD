Composite: treat one and many the same

Files and folders share one interface. The client calls root.size(). Each folder asks its children and adds up the answers, so calls flow down and sums flow up. Nobody checks "is this a file or a folder?".

The code (lines light up with the steps)

interface FsNode { name: string; size(): number }class File implements FsNode {           // leaf  size() { return this.kb; }}class Folder implements FsNode {         // composite  private children = new Map<string, FsNode>();  size() {    let s = 0;    for (const c of this.children.values()) s += c.size();    return s;  }  add(n: FsNode) {    if (n instanceof Folder && this.isInside(n)) throw 'EINVAL';    this.children.set(n.name, n); n.parent = this;  }}

Try it: grow the tree


    

    

      
Say this in the interview

      
"A directory holds files and other directories, so I use Composite. File and Directory both implement FsNode. A directory keeps its children as FsNode, and its size() is the sum of its children's size(). The caller calls root.size() and never checks types. add() lives only on Directory, and a parent pointer gives me path() and the guard against moving a folder into its own child."

    

    

      
Check yourself

      
Why are a folder's children typed as FsNode and not File?
So folders can nest and any future node type (symlink, zip archive) fits without changing Folder.

      
Should add() be on the interface?
If it is, File.add() must throw at runtime, which breaks LSP. In TypeScript, keep add() on Folder so misuse is a compile error.

      
size() is called very often on a big tree. Fix?
Cache the size in each folder; on every change walk up the parent pointers and adjust ancestors. Reads O(1), writes O(depth).

      
Composite vs Decorator?
Both share the component's interface. A decorator wraps one object to add behaviour; a composite holds many children and combines their results.
