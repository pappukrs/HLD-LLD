Decorator

Wrap an object in another object with the same interface that adds behaviour before or after the call. Stack wrappers like layers of an onion. The order of the layers is a design decision, and you can watch it change the result.

Say this in the interview

"I keep EmailNotifier simple and add retry, logging and rate limiting as decorators that implement the same Notifier interface. I compose them once in the composition root, and the service doesn't know they exist. The order is deliberate: rate limit outermost so one user call costs one token, logging outside retry so we log the total time the user waited. Retry is only safe because the send carries an idempotency key."

Check yourself

Retry inside or outside the rate limiter?
Rate limit outside retry: one token per user call, retries are free. Retry outside the rate limiter: every attempt costs a token, which protects the provider better. Choose on purpose and say why.
new Retry(new Logging(gw)); the gateway fails twice then succeeds. How many "start" log lines?
Three, one per attempt, because logging is inside the retry. With new Logging(new Retry(gw)) you get one.
Why not RetryingLoggingEmailNotifier via inheritance?
Every combination needs its own subclass (class explosion), and the combination is fixed at compile time. Decorators combine at runtime, and each one is tested alone.
Is NestJS's @Injectable() the Decorator pattern?
No. It is a TypeScript language decorator that attaches metadata for DI. A method decorator like @Retry(3) that wraps the method can implement the pattern, but the GoF pattern is about wrapping objects at runtime.
