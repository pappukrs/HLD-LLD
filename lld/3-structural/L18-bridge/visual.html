Bridge: split two axes into two hierarchies

Message kind and delivery channel change independently. Inheritance on both gives one class per pair (M × N). Bridge gives the kind a channel field, so each side grows on its own (M + N) and the channel can be switched at runtime.

The bridge in code

interface Channel {                    // implementor
  maxLength: number;
  deliver(to: string, body: string): Promise<void>;
}

abstract class Notification {          // abstraction
  constructor(protected channel: Channel) {}   // the bridge
  setChannel(c: Channel) { this.channel = c; }
  protected abstract body(): string;
  send(to: string) {
    const text = this.body().slice(0, this.channel.maxLength);
    return this.channel.deliver(to, text);
  }
}

class OtpNotification extends Notification {
  protected body() { return `OTP ${this.code}. Valid 5 min.`; }
}
new OtpNotification(new SmsChannel(), '482913').send(user);

Try it: count the classes, send a message

Pick any kind with any channel. No class like OtpSms is needed.

Say this in the interview

"Notifications vary on two axes: what we send and how we deliver it. Inheritance on both gives M × N classes like OtpSms, with SMS code copied in each. So I use Bridge: Notification holds a Channel. Kinds own the content and rules; channels own delivery. A new channel or a new kind is one class, and I can switch channels at runtime for fallback."

Bridge vs Adapter?
Bridge is chosen up front so two hierarchies can grow independently. Adapter is a retrofit that makes one existing class fit an interface you already have. Concrete channels are often adapters over vendor SDKs.
Bridge vs Strategy?
Strategy swaps one algorithm and usually only the strategy side grows. Bridge splits a whole class into two hierarchies, and both sides grow.
SMS has a 160-character limit. Where does that knowledge live?
In the channel (maxLength). The abstraction reads it. Never write instanceof SmsChannel inside Notification.
