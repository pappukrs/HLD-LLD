Abstract Factory

A payment provider is not one object. It is a client, a webhook verifier and a refund API that only work together. One factory per provider (a "kit") creates the whole family, so you can never mix provider A's client with provider B's verifier.

Say this in the interview

"Each payment provider has a client, a webhook verifier and a refund API that only work together. I define a ProviderKit interface with one create method per product, and one kit per provider. The composition root picks the kit from config and injects it, so the service can never mix provider A's client with provider B's verifier. Tests inject a FakeKit. The cost: adding a new product type means editing every kit."

Check yourself

What bug does Abstract Factory prevent that two separate factories do not?
Mixing families. With two independent factories driven by two config values, you can end up with a Stripe client and a Razorpay webhook verifier. Every webhook then fails signature checks. One kit creates all products from the same family.
You need to add createPayoutApi(). What changes?
The ProviderKit interface and every concrete kit (Razorpay, Stripe, Fake). That is the known weakness: adding a new family is easy, adding a new product kind is not.
Is a NestJS module with useClass chosen by env an abstract factory?
Close in spirit. A dynamic module that registers a whole set of matching providers (client, verifier, refunder) for one provider from config gives the same "one family at a time" guarantee.
