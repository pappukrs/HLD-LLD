class PaymentOrderBuilder {  private o: Draft = { currency: 'INR', capture: 'auto', notes: {} };  forCustomer(id: string) { this.o.customerId = id; return this; }  amountInPaise(p: number) { this.o.amount = p; return this; }  manualCapture() { this.o.capture = 'manual'; return this; }  captureWithin(h: number) { this.o.captureWithinH = h; return this; }  build(): Readonly<PaymentOrder> {    if (!this.o.customerId) throw new ValidationError('customerId required');    if (!(this.o.amount! > 0)) throw new ValidationError('amount must be > 0');    if (this.o.capture === 'manual' && !this.o.captureWithinH)      throw new ValidationError('manual capture needs captureWithin');    return Object.freeze({ ...this.o, notes: { ...this.o.notes } });  }}

Say this in the interview

"A payment order has many optional fields and rules between them, like 'manual capture needs a capture window'. I use a builder with named methods, keep defaults inside it, and check every rule once in build(). The result is frozen, so the rules stay true. For a simple object with independent fields I'd just use an options object, since TypeScript already gives named fields."

Check yourself

Why validate in build() and not in each setter?
Some rules involve several fields ("manual capture needs captureWithin"). While the builder is half filled, those rules are not checkable yet. build() is the one moment when all fields are known.
Why copy notes into the result instead of passing the same object?
So later calls on the builder (.note('x', 'y')) cannot change an object that was already built and validated. Object.freeze is shallow, so nested objects need their own copy (and freeze if you want).
Builder vs Factory?
Factory decides which class to create, in one call. Builder decides how to assemble one object over several calls. They can combine: a factory returns a pre-filled builder.
