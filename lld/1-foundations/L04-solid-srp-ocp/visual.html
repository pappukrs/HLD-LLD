SOLID part 1: SRP and OCP

One OrderService validates, applies coupons, charges, saves and emails. Five teams edit it. We split it by reason to change (SRP), then make coupons pluggable so a new one is a new class, not an edit (OCP).

The code behind the scene

Say this in the interview

"OrderService changes for five teams, so I split it by reason to change and keep it as the coordinator. Coupons are what you'll extend, so pricing depends on a Discount interface with one class per coupon, registered in the composition root. A new coupon is a new class and one line; nothing that works gets edited."

Check yourself

Is SRP "one method per class"?
No. It is one actor, one reason to change. A class may have many methods if the same team changes all of them for the same reason.
The coupon map lives inside PricingService. Is that OCP?
Not fully: adding a coupon still edits PricingService. Register discounts from the composition root, or pass them into the constructor.
Should Order (the entity) get an interface too?
No. It does not vary. Put seams where change is likely (coupons, payment, notifications) and around I/O. Extra interfaces cost reading time.
After the split, why does OrderService still exist?
It owns the flow: validate, price, charge, save, notify. That sequence is its one reason to change.
