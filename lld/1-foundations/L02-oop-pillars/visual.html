Say this in the interview

"Each entity owns its state and exposes behaviour, not setters: Wallet.debit() checks the balance, so the rule lives in one place. Payment methods sit behind an interface, so checkout calls method.pay() with no type switch. I use inheritance only for a shallow base that shares validation; everything else is composition."

Check yourself

Private fields plus a public setter for each one: is that encapsulation?
No. The rules still live outside. Encapsulation means the class offers meaningful operations (debit, hold, book) that keep its invariants true.
Abstraction vs encapsulation?
Encapsulation protects data and rules inside one object. Abstraction is the small contract a caller depends on so it can ignore implementation details.
Why did the deep tree in the last step hurt?
Every level depends on the one above. A change in Vehicle ripples to every subclass, and each must be re-tested. Shallow trees plus composition keep changes local.
Where does JS find doPay when pay() calls this.doPay()?
On this, the real object, walking its prototype chain from the bottom. So it finds the child's override first. That is dynamic dispatch.
