Say this in the interview

"Postgres is the source of truth; changes flow through the outbox and Kafka into Elasticsearch, about a second behind. Each term maps to a sorted posting list, an AND query is a merge of lists, and BM25 plus business boosts ranks the hits. For typeahead, a daily job builds a trie from query logs with the top 10 stored at every node, served from memory, with client debounce and CDN caching for short prefixes."

The key lines

// AND = merge sorted posting lists
while (i < a.length && j < b.length) {
  if (a[i] === b[j]) { out.push(a[i]); i++; j++; }
  else if (a[i] < b[j]) i++; else j++;
}
// typeahead = walk prefix, read cached list
for (const ch of prefix) node = node.children.get(ch);
return node.top;   // O(prefix + k)

Check yourself

Why must index time and query time use the same analyser?
The index stores "run". If the query is not stemmed, "running" looks for a term that does not exist and nothing matches.
Why are posting lists kept sorted by doc id?
So AND is a linear two-pointer merge that never goes back, and lists compress well (store gaps between ids).
A doc was written 200 ms ago and is not in results. Why?
It is in the in-memory buffer. It becomes searchable at the next refresh, by default every 1 second.
What does caching top-k in each trie node cost?
Memory (k entries per node) and slower updates, because every node on the path must be re-ranked. That is fine because the trie is rebuilt offline.

Numbers

  • ES refresh: 1 s by default (near-real-time)
  • Shards: about 10 to 50 GB each
  • Deep paging limit: 10,000 hits; use search_after
  • Typeahead: ~100 ms keystroke to screen, 100 to 200 ms debounce
  • BM25 defaults: k1 = 1.2, b = 0.75
