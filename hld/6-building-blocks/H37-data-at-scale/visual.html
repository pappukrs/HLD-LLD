Data at scale: fan-out, hot keys, counters

Top: a home feed built by push, by pull, and by a hybrid that keeps celebrities off the write path. Bottom: one viral post's like counter melts a cache node until the key is split, while the like table stays the truth.

Say this in the interview

"Reads are about 100 times writes, so I fan out on write: workers push post ids into each active follower's Redis list, capped at 800 ids. Authors above about 100k followers are not pushed; their recent posts are merged at read time. For a viral post, likes go to 16 split counter keys and reads sum them, with a 1-second local cache. The likes table with a unique (user_id, post_id) stays the source of truth."

The key lines

// hybrid fan-out
if (author.followers >= CELEB) return;   // pull later
for (f of activeFollowers) {
  LPUSH tl:{f} postId; LTRIM tl:{f} 0 799
}
// split hot counter
INCR likes:{post}#{rand(0..15)}
total = sum(MGET likes:{post}#0..#15)

Check yourself

Why does adding Redis nodes not fix one hot key?
A key hashes to one slot on one node. New nodes take other keys. Split the key into sub-keys, replicate it for reads, or cache it locally.
Why store ids, not post bodies, in timelines?
Memory (6.4 KB per user for 800 ids) and one place to edit or delete. Bodies come from a post cache at read time.
A pushed post is deleted. Do you clean 2,000 lists?
No. Mark it deleted in the posts store; hydration drops it. Clean lists lazily.
Why keep a likes table if you have a counter?
The unique (user_id, post_id) row stops double likes and lets a job rebuild the count. The counter is a derived cache.

Numbers

  • One Redis key: ~100k simple ops/s on one core
  • DynamoDB partition: 3,000 RCU, 1,000 WCU
  • 800 ids x 8 B = 6.4 KB per timeline; 100M users ≈ 640 GB
  • Celebrity limit: about 10k to 100k followers
