Batch and stream processing

Clicks arrive out of order. A stream job puts each one in a 1-minute window by event time, fires a window when the watermark passes it, survives a crash with checkpoints and upserts, and a nightly batch job fixes what the stream missed.

Event in flight Counted in a window Window fired / exact Late / crash

Say this in the interview

"Clicks go to Kafka keyed by ad id. Flink counts them in 1-minute tumbling windows by event time, with a watermark 30 seconds behind the max event time; late events go to a side output. Results are upserted into ClickHouse by (ad, window), so a replay after a crash overwrites instead of double counting. A nightly Spark job recomputes exact counts from raw S3 data, and we bill on those."

The key lines

const start = floor(e.t / 60) * 60;     // event-time window
if (start + 60 <= watermark) return late(e);
count[start][e.ad]++;
maxT = max(maxT, e.t);
watermark = maxT - 30;                  // allowed delay
if (start + 60 <= watermark)             // fire
  sink.upsert(`${ad}|${start}`, n);     // idempotent

Check yourself

Why count by event time, not processing time?
Events arrive late and out of order (offline phones, consumer lag). Processing time puts a click in whatever minute the job happened to see it, so counts move when the system is slow.
What decides when a window fires?
The watermark: when it passes the window's end, the job assumes no more events for that window will come and emits the result.
Checkpoints are exactly-once. Why do we still need an upsert sink?
After a crash the job replays from the last checkpoint and emits results again. An increment sink counts them twice; an upsert by (ad, window) just overwrites.
Why keep a nightly batch job if the stream works?
The batch sees the complete data, including late events dropped by the stream, and is easy to rerun. Money numbers come from batch; the stream is for speed.

Numbers

  • Kafka to Flink to OLAP: a few seconds end to end
  • Checkpoints: every 10 s to a few minutes
  • 10B events/day x 200 B = 2 TB/day raw, ~300 GB as Parquet
