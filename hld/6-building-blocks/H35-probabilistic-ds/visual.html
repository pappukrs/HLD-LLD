Bloom filter, Count-Min sketch, HyperLogLog

Three tiny structures that trade a small, one-sided error for huge memory savings. Bloom: "definitely not / maybe yes". Count-Min: "about how many times, never less". HyperLogLog: "about how many distinct".

Try it on: Bloom filter Acts on whatever structure is on screen. Bloom: add a word, or check it. Count-Min: add one event, or estimate its count. HyperLogLog: add a user id and watch the estimate. Enter = check, Shift+Enter = add. Reset returns to the demo data.

Say this in the interview

"I'll put a Bloom filter in front of the database. For a key that does not exist, the filter says 'no' and we skip the read. It can give false positives but never false negatives. For 1% false positives I need about 10 bits per item and 7 hashes, so 1 billion keys fit in about 1.2 GB."

"For trending hashtags I use a Count-Min sketch plus a min-heap of size k. The sketch can only overcount, by at most ε times the total. For unique visitors I keep one HyperLogLog per page per hour in Redis: 12 KB each, 0.81% error, and I merge hours into days with PFMERGE. Billing numbers stay exact in the batch path."

The one-sided error is the point

  • Bloom: never a false "no". A "maybe" costs one real lookup.
  • Count-Min: never undercounts. Collisions only add, so take the minimum row.
  • HyperLogLog: two-sided but small, ±1.04/√m. Mergeable with a max per register.
  • Pick the structure whose wrong answer is cheap for your use case.
  • Never use them where money or a legal number depends on the result.

Check yourself

Why can a Bloom filter never say "no" for an item you added?
Adding sets all k bits of the item to 1, and bits never go back to 0. A "no" needs at least one 0 bit among the item's k bits.
Count-Min says #diwali appeared 2 times, but it never appeared. Is the sketch broken?
No. Every counter it read was shared with other tags. Collisions only add, so the estimate is an upper bound: the true count is between 0 and 2. Wider rows (more columns) make it tighter.
Why can you merge two HyperLogLogs but not add two distinct counts?
Adding counts double-counts users seen in both hours. HLL merge takes the max per register, which is exactly the HLL of the union.
The Bloom filter is full and false positives hit 20%. What now?
It cannot grow in place. Rebuild a bigger one from the source of truth, or use a scalable Bloom filter that adds a new, larger layer (RedisBloom supports this).
