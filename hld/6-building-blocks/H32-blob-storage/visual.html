Blob storage and large files

The API signs a URL; the bytes go straight to the object store in parallel parts. A worker checks the file, the DB row flips to READY, a CDN serves reads, and lifecycle rules move old files to cheap tiers.

Request / bytes in flight Signed / done Failed part / orphan Verified / READY

Say this in the interview

"Bytes go to S3, metadata goes to Postgres. The client gets a presigned PUT for one key, valid 15 minutes, and uploads directly. Big files use multipart with 16 MB parts in parallel, so a failed part is retried alone. An ObjectCreated event triggers a worker that verifies and scans the file and marks it READY. Reads go through a CDN or a short presigned GET, and lifecycle rules move old files to Glacier."

Check yourself

Why is the object key chosen by the server, not the client?
If the client picks the key it can overwrite another user's file. The server builds the key from the user id and a new file id, and signs only that key.
Why wait for the S3 event instead of the client's "done" call?
The client can lie or crash. The event (or a HEAD on the key) proves the object exists and lets you check size and checksum before you mark it READY.
What does a lifecycle rule for incomplete multipart uploads fix?
Parts of uploads that never completed are billed but invisible. "Abort incomplete multipart uploads after 7 days" deletes them.
How do you serve a private bank statement?
Auth check in the API, then a presigned GET valid for about 60 seconds, or a signed CDN URL. Never a public bucket.

Numbers

  • S3: 11 nines durability, strong read-after-write since Dec 2020
  • Single PUT up to 5 GB; object up to 5 TB
  • Multipart: parts 5 MB to 5 GB, at most 10,000 parts
  • ~3,500 writes/s and ~5,500 reads/s per key prefix
  • Erasure coding 6+3: 1.5x raw space vs 3x for replication
