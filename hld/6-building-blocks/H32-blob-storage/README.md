> **Builds on:** [H10 CDN](../../2-scaling/H10-cdn/README.md) · [H04 API design](../../1-basics/H04-api-design/README.md) · [H20 Message queues](../../4-async/H20-message-queues/README.md) · [H02 Back-of-envelope](../../1-basics/H02-back-of-envelope/README.md) · **Used in:** File storage (Dropbox), Video streaming, Photo sharing, Chat system (attachments)

## The idea in one line

File bytes go to an object store (S3, GCS, Azure Blob); your database keeps only the metadata; clients upload and download **directly** with short-lived signed URLs, and a CDN serves the reads.

## Why it matters (the problem it solves)

Put a 200 MB video in a Postgres `BYTEA` column, or stream it through your Node API pods, and you get:

- a database that is mostly bytes: backups take hours, replicas lag, the buffer cache is full of video
- API pods that spend their memory and network copying bytes, so you scale them by GB, not by requests
- an upload that fails at 95% and starts again from zero on a phone network
- no cheap place for files nobody opens after a month

Object storage solves all four: almost unlimited capacity, 11 nines of durability, pay per GB, a plain HTTP API, and storage classes for cold data. Every "design Dropbox / YouTube / Instagram / WhatsApp media" question needs this block.

## How it works

### Block vs file vs object storage

| Type | Access | Example | Use for |
|---|---|---|---|
| Block | Raw blocks, mounted by one machine | EBS, local NVMe | Databases, OS disks |
| File | POSIX paths, shared mount | EFS, NFS | Legacy apps that need a shared filesystem |
| Object | `PUT / GET bucket/key` over HTTP, whole objects + metadata | S3, GCS, MinIO | Images, video, backups, logs, data lakes |

Two facts about objects:
- They are **immutable as a whole**. You replace an object; you cannot edit byte 500 in place.
- Keys look like paths (`users/42/avatar.jpg`) but the namespace is **flat**. The "folder" is just a key prefix.

### The split: metadata in the DB, bytes in the store

```
files table (Postgres)                       S3 bucket
+----+-------+---------------------+------+   +--------------------------------+
| id | owner | s3_key              |status|   | u/42/f/123/v1   (180 MB bytes) |
|123 |  42   | u/42/f/123/v1       |READY |-->| u/42/f/124/v1   (2 MB bytes)   |
|124 |  42   | u/42/f/124/v1       |UPLOAD|   +--------------------------------+
+----+-------+---------------------+------+
  + size, content_type, sha256, created_at
```

The row is small and queryable (list my files, search by name, quota). The bytes live where bytes are cheap.

### Upload flow with presigned URLs

```
Client            API                 Metadata DB        S3              Queue -> Worker
  | POST /uploads   |                      |               |                    |
  |  name,size,type |-- insert UPLOADING ->|               |                    |
  |<- presigned PUT URL (15 min, one key) -|               |                    |
  |------------------- PUT bytes directly ---------------->|                    |
  |                 |                      |               |-- ObjectCreated -->|
  |                 |                      |<---- READY, size, sha256 ----------| scan, thumb,
  | GET /files/123  |                      |               |                    | transcode
  |<- CDN URL or presigned GET URL --------|               |                    |
```

- The API **never touches the bytes**. It only signs a URL that allows one operation on one key for a short time. The signature is computed locally with the secret key (HMAC); no call to S3 is needed.
- **Scope the URL tightly:** exact key (generated by the server, never by the client), content type, max size (a presigned **POST** policy can enforce `content-length-range`), expiry 5 to 15 minutes.
- **Do not trust the client's "upload done" call.** Confirm through the storage event (S3 → SQS/EventBridge) or a `HEAD` on the key, and check size and checksum.
- Process asynchronously: virus scan, EXIF strip, thumbnails, video transcode. Only then flip the row to `READY`.

### Large files: multipart upload

```
200 MB file  ->  [p1 16MB][p2 16MB][p3 16MB] ... [p13 8MB]
                   |        |        X  retry p3 only
                   v        v        v
CreateMultipartUpload -> UploadPart x13 (parallel, 4-6 at a time) -> CompleteMultipartUpload(ETags)
```

- S3 parts are **5 MB to 5 GB**, at most **10,000 parts**, single PUT max **5 GB**, object max **5 TB**.
- Each part is retried on its own. The client stores `uploadId` and the finished part numbers (or asks `ListParts`) to **resume** after a crash.
- Parallel parts use the full link: 4 parallel streams often give 3 to 4 times the speed of one stream on a long, fat connection.
- Add a lifecycle rule `AbortIncompleteMultipartUpload after 7 days`, or you pay for orphaned parts forever.

### Chunking and dedup (Dropbox-style sync)

- Split the file into blocks (fixed 4 MB, or content-defined chunks), name each block by its **SHA-256**.
- Client sends the list of hashes first; the server says which ones it is missing; the client uploads only those.
- Results: **resumable** uploads, **dedup** across users (same video, stored once), and **delta sync** (edit one page of a 1 GB file, upload one 4 MB block).
- Keep a **reference count** per block. Delete a block only when no file version uses it.
- Content-defined chunking (rolling hash, like Rabin) keeps boundaries stable when you insert bytes at the start; fixed chunks would all shift.

### Downloads

| Content | How to serve |
|---|---|
| Public (product images, avatars) | CDN in front of the bucket, long TTL, **versioned keys** (`logo.v3.png`) so you never need to purge |
| Private (KYC docs, bank statements, invoices) | Short-lived **presigned GET** (60 s to 15 min), or CDN with signed cookies/URLs. Never a public bucket |
| Video | Transcode to several bitrates, segment for HLS/DASH (2 to 6 s chunks), CDN serves segments; player switches bitrate |
| Large downloads | HTTP `Range` requests, so a broken download resumes from the last byte |

### Durability: replication vs erasure coding

| | 3x replication | Erasure coding (e.g. 6 data + 3 parity) |
|---|---|---|
| Raw space | 3.0x | 1.5x |
| Survives | 2 lost copies | any 3 lost fragments |
| Read cost | read one copy | read 6 fragments, decode if some are missing |
| Good for | small, hot objects | large and colder data at scale |

S3 spreads data across at least 3 Availability Zones. You still turn on **versioning** (protects from your own bad deletes) and **object lock** (WORM, for audit and regulatory records).

### Cost and lifecycle

```
day 0 -------- day 30 ----------- day 90 -------------- day 365
S3 Standard -> Standard-IA -----> Glacier Flexible ---> Deep Archive (or delete)
~$0.023/GB      ~$0.0125/GB        ~$0.0036/GB           ~$0.001/GB
```

Lifecycle rules move objects by age. Cold tiers charge for **retrieval** and have a minimum storage duration, so do not put files there that users still open.

### Keeping DB and store consistent

Two systems means two failure shapes:
- **Row without object**: upload never finished. Expire `UPLOADING` rows older than N hours.
- **Object without row**: row insert failed or row deleted. A sweeper lists keys (or S3 Inventory) and deletes unreferenced objects after a grace period.

Delete flow: mark row `DELETED` first, then delete the object async (or rely on versioning plus a lifecycle rule).

## In TypeScript

```ts
// The API signs; it never streams the bytes.
async function createUpload(userId: string, name: string, size: number, type: string) {
  if (size > MAX_BYTES) throw new Error('too large');
  const fileId = randomUUID();
  const key = `u/${userId}/f/${fileId}/v1`;            // server picks the key
  await db.files.insert({ id: fileId, owner: userId, key, size, type, status: 'UPLOADING' });
  if (size <= 100 * MB) {
    return { fileId, url: presignPut(key, { contentType: type, expiresIn: 900 }) };
  }
  const uploadId = await s3.createMultipartUpload(key);
  const parts = Math.ceil(size / PART_SIZE);            // e.g. 16 MB parts
  return { fileId, uploadId, urls: range(1, parts).map((n) => presignPart(key, uploadId, n)) };
}

// Worker: triggered by ObjectCreated, not by the client.
async function onObjectCreated(key: string) {
  const head = await s3.head(key);
  const row = await db.files.byKey(key);
  if (!row || head.size !== row.size) return quarantine(key);
  await scanAndThumbnail(key);
  await db.files.update(row.id, { status: 'READY', sha256: head.checksum });
}
```

The full runnable version in [demo.ts](demo.ts) simulates a flaky network: multipart upload with per-part retry, block dedup across two users, and the lifecycle cost of 1 year of photos.

## Trade-offs / when NOT to use it

| Option | Use when | Weakness |
|---|---|---|
| Bytes in the DB | Tiny files (under ~100 KB), few of them, must be in the same transaction as the row | DB bloat, slow backups and replicas |
| Object store + metadata row | Almost always | Two systems to keep in sync (orphans, dangling rows) |
| Upload through your API | Must inspect or transform the stream inline, or tiny files | API bandwidth and memory, slower |
| Presigned direct upload | Default for anything over a few hundred KB | Must verify after upload; scope the URL carefully |
| Erasure coding | Large, colder data at scale | CPU to decode, slower rebuild |
| Self-hosted (MinIO, Ceph) | Data residency, or cost at Dropbox scale | You own durability and on-call |

Not a fit: data you need to update in place byte by byte (use a database or block storage), or millions of tiny records you need to query (that is a database job; S3 charges per request, so 1 KB objects are expensive).

## Common mistakes

- Streaming uploads through the API "for security". Signed URLs are the security: one key, one verb, 15 minutes.
- Letting the client choose the object key. A user can then overwrite someone else's file. The server generates keys.
- Marking the file READY when the client says "done", with no `HEAD` or event check.
- Forgetting the lifecycle rule for incomplete multipart uploads; orphaned parts silently cost money.
- Public bucket for private documents. Use presigned GET or signed CDN URLs.
- Purging the CDN on every update instead of using versioned keys.
- Saying "S3 is eventually consistent". Since December 2020, S3 gives **strong read-after-write** consistency for PUT and DELETE.
- Putting all objects under one hot prefix at very high RPS. Each prefix handles about 3,500 writes and 5,500 reads per second; spread keys (for example a hash prefix).

## Say this in the interview

> "File bytes go to S3. Postgres keeps only metadata: owner, key, size, checksum, status. The client asks the API for a presigned PUT URL that allows one key for 15 minutes, then uploads directly to S3, so the API never carries bytes. Files over about 100 MB use multipart upload with 16 MB parts in parallel, so a broken part is retried alone and the upload can resume."

> "An S3 ObjectCreated event goes to a queue. A worker checks size and checksum, scans the file, makes thumbnails or transcodes, and only then marks the row READY. Public reads go through a CDN with versioned keys. Private files get a presigned GET valid for a minute. Lifecycle rules move files older than 90 days to Glacier, and a sweeper cleans orphaned rows and objects."

> "For a sync product like Dropbox I would chunk files into 4 MB blocks named by SHA-256. The client sends hashes first and uploads only the missing blocks. That gives dedup across users and delta sync for small edits."

## Your experience hook

- Payment orchestration (SenseGrass): invoices, receipts and KYC documents are the classic private-file case. Say how you would store them: S3 with KMS encryption, a row with status and checksum in the DB, and only short-lived presigned GET URLs after an auth check.
- IoT platform (Matriot): you already batched high-frequency device writes. Raw telemetry archives follow the same idea at file level: batch into large compressed objects per device per hour in S3, then lifecycle them to a cold tier.
- For Mediasoup video calls, call recordings would be written by the media server to S3 with multipart upload, then a worker transcodes to HLS for playback.

## Numbers to remember

| Fact | Value |
|---|---|
| S3 durability (designed) | 99.999999999% (11 nines) |
| S3 Standard availability SLA | 99.9% |
| Consistency | Strong read-after-write for PUT and DELETE (since Dec 2020) |
| Max object / max single PUT | 5 TB / 5 GB |
| Multipart part size / max parts | 5 MB to 5 GB / 10,000 |
| Request rate per prefix | ~3,500 writes/s and ~5,500 reads/s |
| S3 Standard price | ~$0.023 per GB-month (Glacier Deep Archive ~$0.001) |
| Estimation | 1M photos/day x 2 MB = 2 TB/day, about 730 TB/year before replicas |
| Dropbox block size | 4 MB |

## Self-test

<details><summary>1. Why not stream uploads through the API servers?</summary>

They become bandwidth and memory bottlenecks and have to scale with bytes, not requests. A 1 Gbps pod can carry only about 125 MB/s in total. Direct-to-S3 uploads move that load to a system built for it.
</details>

<details><summary>2. What two inconsistencies appear between the metadata DB and the object store, and how do you fix them?</summary>

A row with no object (upload never finished) and an object with no row (insert failed or row deleted). A sweeper expires old `UPLOADING` rows and deletes unreferenced objects after a grace period.
</details>

<details><summary>3. How do you resume an upload that broke at 80%?</summary>

With multipart, the client keeps the `uploadId` and finished part numbers (or calls `ListParts`) and uploads only the missing parts, then calls Complete. With hashed blocks, the server reports which hashes it already has.
</details>

<details><summary>4. How do you stop a user uploading 10 GB to a profile-photo endpoint?</summary>

Use a presigned POST with a `content-length-range` and content-type condition, generate the key on the server, and check size and type again in the worker; delete anything that fails.
</details>

<details><summary>5. How do you deduplicate identical files across users safely?</summary>

Name blocks by content hash. The client sends hashes first; the server returns the missing ones. Keep a reference count per block and delete a block only when the count reaches zero. Check that the uploaded bytes really hash to the claimed value.
</details>

<details><summary>6. Replication or erasure coding for 50 PB of user photos?</summary>

Erasure coding for most of it: about 1.5x raw space instead of 3x saves around 75 PB of disk. Keep hot, small objects replicated for fast reads.
</details>

<details><summary>7. When is storing a file in the database acceptable?</summary>

Small files, low volume, and you need them in the same transaction as the row, like a tiny signature image. Otherwise use an object store.
</details>

<details><summary>8. A private PDF link was shared on Twitter. What limits the damage?</summary>

A short presigned GET expiry (for example 60 seconds), generated per request after an auth check. The leaked link dies fast. A public bucket or a long-lived URL would leak forever.
</details>
