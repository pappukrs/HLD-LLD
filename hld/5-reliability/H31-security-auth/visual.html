Login, Tokens and Access Checks

Follow a user through OAuth2 authorization code + PKCE, get a JWT, and call an API. Then watch the attacks fail: a stolen code, a tampered token, someone else's order id, and a reused refresh token. Authentication says who you are; authorization is checked on every resource.

Say this in the interview

"Users sign in with OIDC, authorization code + PKCE. The provider issues a 10-minute RS256 access token and a rotating refresh token. The gateway verifies signature, expiry, issuer, audience and scope locally with cached JWKS keys. Each service still scopes every query by the caller, so another user's order id returns 404. Services talk over mTLS."

Checks in order

  1. alg is on the allow-list (never none).
  2. Signature valid with the public key for kid.
  3. exp not passed (allow ~30 s skew); iss and aud match.
  4. Scope allows the action (gateway).
  5. Caller owns the resource (service, in the query).

Check yourself

Why did the stolen code fail in step 5?
The token endpoint wants the code_verifier whose SHA-256 equals the challenge sent at the start. Only the real app has it.
The payload is readable. Is that a problem?
Only if you put secrets or PII in it. It is signed, not encrypted. Keep it to ids, scopes and expiry.
Why 404 and not 403 for someone else's order?
403 confirms the order exists, which helps an attacker enumerate ids. 404 reveals nothing.
Why revoke the whole family on refresh token reuse?
A rotated token should never come back. If it does, one copy is stolen and you cannot tell which, so you cut both and force a fresh login.
