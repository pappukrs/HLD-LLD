Consensus, Leader Election and Fencing

Raft keeps five servers agreeing on one leader and one log, as long as a majority is alive. On top of it, etcd hands out locks as leases with a growing number. The number matters: a paused worker can wake up after its lease ended, and only a fencing token stops its stale write.

Say this in the interview

"The scheduler instances elect a leader through an etcd lease. etcd is a 5-node Raft cluster, so it survives 2 failures and a minority partition can never elect a second leader. Each payout run carries the lease revision as a fencing token, and the payouts table rejects lower tokens, so a paused old leader cannot pay twice. The payout is idempotent by batch id as a second guard."

Raft rules on one card

  • One vote per node per term.
  • Vote only for a log at least as new as yours.
  • Commit when a majority stores the entry.
  • See a higher term → become a follower.
  • Random election timeouts avoid split votes.

Check yourself

5 nodes tolerate how many failures? 6 nodes?
Both tolerate 2. Majority of 5 is 3; majority of 6 is 4. Use odd sizes.
Why did S5 lose the election in step 4?
Its log ended at term 1, but S1 and S2 had a committed entry from term 2. Nodes vote only for logs at least as new as theirs, so a node missing committed data can never become leader.
Why not just choose a longer lock TTL?
A pause (GC, VM freeze, network stall) can be longer than any TTL. Only the resource checking the token can tell a stale holder from the current one.
Can an old leader still serve reads?
Yes, briefly, and they may be stale. Linearizable reads use ReadIndex (confirm leadership with a heartbeat round) or go through the log.
