Unique IDs: Snowflake and Base62

Auto-increment breaks once data is sharded. A Snowflake id packs time, a worker id and a counter into 64 bits, so every pod can make unique, roughly time-sorted ids with no network call. Watch the bits fill, the sequence overflow, the clock go backwards, and a short code come out of base62.

Say this in the interview

"Each pod generates 64-bit Snowflake ids in memory: 41 bits of milliseconds since our epoch, 10 bits of worker id leased from etcd, 12 bits of sequence. That is 4,096 ids per ms per pod, no network call, and ids sort roughly by time. If the clock goes back, the generator waits. Ids go out as strings in JSON. Short links use a range allocator plus base62 instead, for 7-character codes."

The four rules of the generator

  • Same ms as last id: seq++. New ms: seq = 0.
  • seq passes 4,095: wait for the next ms.
  • Clock behind lastMs: refuse or wait. Never reuse an old time.
  • Worker id must be unique among live pods: lease it, never guess it.

Check yourself

6,000 requests arrive in one millisecond on one worker. What happens?
The first 4,096 get sequence 0–4,095. Then the generator waits for the next ms and continues from sequence 0.
Why must the generator refuse when the clock goes backwards?
With the same worker id and an earlier time, it could build a (time, seq) pair it already used. That is a duplicate id.
Why send the id as a string in JSON?
A JS Number is exact only up to 2^53 − 1. A 64-bit id gets rounded by JSON.parse, silently changing it.
Why not use Snowflake for short links?
A 64-bit number is 10–11 base62 characters. A counter from a range allocator stays small, so codes are 6–7 characters.
