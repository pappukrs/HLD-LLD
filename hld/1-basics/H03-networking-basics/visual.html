Networking: DNS, TCP/UDP, HTTP, TLS

Before your server does any work, a new HTTPS request pays for a DNS lookup, a TCP handshake and a TLS handshake. Count the round trips, watch keep-alive and a nearby edge remove them, then see why one lost packet hurts TCP, HTTP/2 and HTTP/3 differently.

Try it: 150 ms
DNS TCP TLS HTTP Lost / stale

Say this in the interview

"A new HTTPS request costs a DNS lookup, one round trip for TCP and one for TLS 1.3 before the request itself, so about three round trips. From Mumbai to us-east that's over half a second. So I terminate TLS at a CDN edge near the user, keep connections alive and pooled, use HTTP/2 or gRPC between services, and deploy in the user's region. HTTP/3 helps mobile users on lossy networks."

Numbers worth remembering

  • Same data centre RTT ~0.5 ms; cross-AZ ~1–2 ms
  • Mumbai ↔ Singapore ~60 ms; Mumbai ↔ us-east ~200+ ms
  • New HTTPS: TCP 1 RTT + TLS 1.3 1 RTT (TLS 1.2: 2) + request 1 RTT
  • QUIC/HTTP/3: 1 RTT to first request, 0 with resumption
  • Ethernet MTU 1,500 B; 1 Gbps = 125 MB/s

Check yourself

Why is the second request so much faster?
DNS is cached and the TCP + TLS connection is reused (keep-alive). Only one round trip plus server time is left.
Why does a CDN edge speed up dynamic APIs too?
The expensive handshakes happen over a short RTT to the edge. The edge reaches the origin over warm, pooled connections, so only the request itself crosses the long distance.
Why does HTTP/2 still have head-of-line blocking?
Its streams share one TCP byte stream. A lost TCP segment holds back every later byte, so every stream waits for the retransmit. QUIC tracks loss per stream.
Why is DNS failover slow?
Resolvers and clients cache the old record until its TTL expires, and some ignore low TTLs. Lower the TTL before a move, or use anycast / a global load balancer with a fixed IP.
