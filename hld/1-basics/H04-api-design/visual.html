Say this in the interview

"Every write a client may retry takes an Idempotency-Key header. The server inserts the key with a unique constraint in the same transaction as the payment row, so a retry replays the first response instead of charging twice. Lists use keyset pagination on (created_at, id), which is one index seek at any depth and does not repeat rows when new ones arrive."

Check yourself

Why not "SELECT key, then INSERT if missing"?
Two retries arriving together both see "missing" and both charge. The insert itself must be the check: a unique constraint or Redis SET NX.
Who generates the key, and when?
The client, once per logical action (one "Pay" tap). Every retry of that action reuses it. A new key per HTTP attempt defeats the point.
Why did offset page 2 repeat posts 8 and 7?
Two new posts landed at the top, pushing every row two places down. Offset 4 now points at what used to be offset 2. A cursor says "older than post 7", which does not move.
When is offset pagination fine?
Small admin tables where "go to page 7" matters and data changes slowly. Not for feeds or deep history.

Where it shows up

  • Stripe and Razorpay accept Idempotency-Key on POST and keep it ~24 h.
  • Slack, X and Stripe list endpoints use cursors.
  • Google, Netflix and Uber run gRPC between services.
  • GitHub and Shopify offer GraphQL next to REST.
