Proxies, reverse proxies and the API gateway

A forward proxy works for clients, a reverse proxy works for servers. An API gateway is a reverse proxy with a pipeline: each stage can stop a request before it ever reaches a service.

Say this in the interview

"Clients hit one domain. An L4 load balancer spreads traffic over stateless gateway instances in several zones. The gateway terminates TLS, adds a request id, verifies the JWT locally with cached keys, applies a per-user token bucket in Redis, and routes by path to the service with a timeout and a circuit breaker. Business logic stays in the services."

Check yourself

Why did the 401 and 429 never reach order-svc?
Each stage can stop the request and reply itself. That is the point of the gateway: bad and excess traffic is rejected once, at the edge, instead of in every service.
Four gateway instances, limit 100/min. A user gets 400. Why?
Each instance counted in its own memory. Keep the counter in Redis (atomic INCR or a Lua script), or hash each user to one instance.
What should never live in the gateway?
Business rules (pricing, coupons, order checks). Otherwise the gateway becomes a new monolith that every team must deploy through.
Gateway vs BFF vs service mesh?
Gateway: front door, north-south traffic. BFF: one thin backend per client type. Mesh: sidecar proxies for service-to-service (east-west) traffic.
