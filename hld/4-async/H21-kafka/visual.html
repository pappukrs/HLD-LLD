Kafka: partitions, consumer groups, offsets

A topic is split into partitions: append-only logs. The key picks the partition, so one key stays in order. In a consumer group each partition has exactly one reader, and the group's position is a committed offset. Reading never deletes.

Try it: durability and sizing

Say this in the interview

"Order events go to a topic keyed by order_id, so all events of one order land in one partition and stay in order. Each downstream service is its own consumer group, so each gets every event and can replay. Partitions are the unit of parallelism, so I create more than I expect consumers. RF 3, min.insync.replicas 2, acks=all. Consumers commit after processing: at-least-once, so handlers are idempotent, and I alert on lag."

Rules to remember

  • Order is per partition, not per topic.
  • Max useful consumers in a group = number of partitions.
  • Adding partitions later changes hash(key) % P, so a key can move and lose order for a while.
  • Reading does not delete. Messages stay for the retention time (7 days default) or forever with compaction.
  • A slow consumer only builds lag; it does not slow the producer.

Kafka vs a classic queue

Kafka (log)RabbitMQ / SQS (queue)
After a message is readIt stays; the group moves its offsetIt is acked and deleted
Many independent readersYes: one consumer group per serviceNeeds a fanout exchange or SNS → many queues
Replay old messagesYes: reset the offsetNo (unless you archive them)
OrderingPer partitionPer queue (SQS FIFO: per message group)
Scaling consumersUp to the partition countAny number of competing consumers
Per-message delay, priority, DLQWeak (build it yourself)Built in
ThroughputMillions of msgs/s per clusterTens of thousands per queue

Check yourself

A topic has 6 partitions and the group has 8 consumers. What happens?
6 consumers get one partition each and 2 stay idle as standbys. If a consumer dies, an idle one takes its partition at the next rebalance.
Commit before or after processing?
After processing gives at-least-once: a crash replays a few messages, so handlers must be idempotent. Before gives at-most-once: a crash loses messages.
How do you stop a rebalance from pausing the whole group?
Cooperative sticky assignor (only moved partitions pause), static membership (group.instance.id) so a quick restart does not trigger a rebalance, and short work per poll below max.poll.interval.ms.
RF=3, min.insync=2, acks=all, two brokers die. Writes?
They fail with NotEnoughReplicas. Nothing acknowledged is lost. Kafka picks consistency over availability here.
