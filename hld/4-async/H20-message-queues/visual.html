Message queues and pub-sub

A queue is a durable buffer between the service that creates work and the service that does it. Watch competing workers, fan-out to one queue per service, ack-after-work, redelivery after a crash, a traffic spike, and a poison message landing in the DLQ.

Try it: will the queue keep up?

Say this in the interview

"The API writes the order and an outbox row in one transaction and returns. A relay publishes order.placed to a topic exchange; email, inventory and analytics each have their own durable queue, and several workers compete on each. Workers ack after the side effect commits, so delivery is at-least-once and every consumer is idempotent on the message id. Failures back off with jitter, and after 5 attempts go to a DLQ we alert on and redrive. Workers autoscale on queue depth."

Rules of thumb

  • One queue per consuming service; many workers per queue.
  • Ack after work. Auto-ack = at-most-once.
  • Backoff + jitter, a max attempt count, and a DLQ with an alert.
  • Little's law: workers = rate × processing time.
  • Redis Pub/Sub stores nothing: only for live signals.

Check yourself

Three services need every order.placed. One shared queue?
No: with one queue each message reaches only one consumer. Bind three queues (one per service) to a fanout or topic exchange, or SNS → three SQS queues.
A worker crashes after charging but before ack. What happens?
The broker redelivers the message to another worker. Without an idempotency key the side effect runs twice. Record the message id in the same transaction as the side effect.
Why backoff with jitter instead of instant retry?
Instant retries hammer a downstream that is already failing, and many workers retrying in lockstep create a retry storm. Exponential backoff spreads them over time; jitter de-synchronises them.
SQS visibility timeout is 30 s, job takes 2 min?
The message reappears and a second worker starts the same job. Raise the timeout above the job's p99 or extend it as a heartbeat with ChangeMessageVisibility.
