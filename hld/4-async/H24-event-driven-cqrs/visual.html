Event-driven, CQRS and event sourcing

The write side checks rules and emits facts. Projectors turn those facts into read models shaped for each screen. With event sourcing, the facts themselves are the database and the current state is a fold over them.

    Say this in the interview

    "The order service owns writes in Postgres and writes an outbox event in the same transaction; Debezium puts it on Kafka keyed by order id. Search, dashboards and loyalty each build their own read model and keep the last applied version per order, so duplicates and replays are no-ops. Read models lag by up to a second, so the user's own order is read from the write side right after checkout. Only the wallet ledger is event-sourced, with expected-version appends and snapshots."

    The two key code lines

    // projector: idempotent and order-safe
if (evt.version <= view.lastVersion) return;

// event store: optimistic concurrency
store.append(streamId, evt, { expectedVersion });
// → ConcurrencyError if someone appended first

    Source of truthCurrent-state tablesWrite DB; read models are derivedThe event stream
    ReadsSame DBSeparate views per query (ES, Redis, Cassandra)Projections only; never query the stream

    Check yourself

    "SendWelcomeEmail" or "UserRegistered": which is the event?
    UserRegistered: a past-tense fact owned by the producer. SendWelcomeEmail is a command to one service.
    How do you add a new read model a year later?
    Start a new consumer group from the earliest offset (long retention or a compacted topic), or bootstrap from a DB snapshot and then stream from its position.
    Two withdrawals at the same version: what stops a double spend?
    Both append with expectedVersion. One wins; the other gets a conflict, reloads the stream, re-checks the balance and retries or rejects.
    How do you delete personal data from an immutable log?
    Crypto-shredding: encrypt personal fields with a per-user key kept elsewhere, and delete the key.
