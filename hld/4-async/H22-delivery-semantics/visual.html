Delivery semantics and idempotency

You cannot get exactly-once delivery over a network that loses acks. Pick where the ack goes (before or after the work), then make the work idempotent so a redelivery changes nothing.

Say this in the interview

"Delivery is at-least-once, so every handler is idempotent. Clients send an Idempotency-Key; I store it with a unique constraint and the saved response in the same transaction as the change. Consumers insert the event id into a processed table in the same transaction as the side effect, then ack. Delivered twice, applied once: an exactly-once effect."

Check yourself

Why not let the broker give exactly-once?
It cannot see your side effects. If you write to Postgres and crash before committing the offset, the message comes back. The dedupe must live where the side effect lives.
Why must the key come from the business action?
A producer retry creates a new message id for the same order. Only a business key (order id, or the client's Idempotency-Key) is the same on every retry.
What does Redis SET NX add or lose here?
It is fast, but not atomic with the DB write and can lose keys on failover. Fine for "don't send two push notifications", not for money.
