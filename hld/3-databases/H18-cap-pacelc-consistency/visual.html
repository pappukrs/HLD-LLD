CAP, PACELC and consistency models

Networks break. When replicas cannot talk, a system must either refuse some requests to stay correct (CP) or answer everything and fix it later (AP). On a healthy day it still trades latency for freshness (PACELC).

Try it: one read, three ways

Say this in the interview

"Partitions will happen, so the choice is what to do during one. Payments and inventory are CP: the minority side rejects and the client retries with the same idempotency key. Carts, likes and feeds are AP: every side accepts and we merge with version vectors or CRDTs. On a healthy day it's PACELC: strong reads pay a round trip to the leader, so I use read-your-writes for a user's own edits and eventual reads for everything else."

Common misreadings

  • "Pick 2 of 3" is wrong: you cannot give up P. You pick C or A while partitioned.
  • CAP's C is linearizability, not the C in ACID.
  • A CP system is still mostly up: only the minority side refuses.
  • Many stores are tunable per request (Cassandra consistency levels, DynamoDB ConsistentRead).

Check yourself

Why can't a 2-node cluster stay CP if the link breaks?
Neither side has a majority (2 of 2 needed), so both sides must stop writes. Consensus clusters use 3 or 5 nodes so that one side can always hold a majority.
What does last-write-wins lose?
Concurrent updates. If both sides add an item to a cart, LWW keeps one and silently drops the other. Clock skew can even make the older write win. A union merge or a CRDT keeps both.
A user edits their profile and the old value shows on refresh. Fix?
Read-your-writes. Return the write's LSN to the client and only read from a replica that has applied it, else read from the leader. Or read from the leader for a few seconds after any write.
What is PACELC for Spanner and for DynamoDB default?
Spanner is PC/EC: it stays consistent and pays latency for it. DynamoDB default is PA/EL: it stays available and answers fast with eventually consistent reads.
