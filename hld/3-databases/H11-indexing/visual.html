Indexes: B+tree, composite, covering

Without an index the database reads every page. A B+tree is wide and shallow, so a lookup is three or four page reads. Column order decides which queries it can serve, and every index makes writes slower.

Try it: which plan does the database pick?

Table: 10M payments, 200k pages, 5,000 merchants (~2,000 rows each), 50% FAILED. Page reads are rough estimates, the way a planner would think about them.

Say this in the interview

"An index is a B+tree side-structure. Each node is an 8 KB page with hundreds of keys, so 100 million rows is three or four levels and the top levels sit in memory. For merchant_id = ? ORDER BY created_at DESC LIMIT 20 I'd index (merchant_id, created_at): equality first, then the sort column, so it seeks once and reads 20 entries in order. On a hot path I'd INCLUDE the selected columns for an index-only scan. I don't over-index, because every index taxes every write."

The key SQL

-- equality first, then sort/range column
CREATE INDEX idx_pay_m_t
  ON payments (merchant_id, created_at DESC)
  INCLUDE (amount, status);   -- covering

-- partial: small index for a rare value
CREATE INDEX idx_pending
  ON orders (created_at) WHERE status = 'PENDING';

-- expression: makes lower(email) seekable
CREATE INDEX idx_email_l ON users (lower(email));

Check yourself

Binary trees are also O(log n). Why do databases use B+trees?
Disks read whole pages. A binary tree reads one key per node (~23 reads for 10M rows). A B+tree fits hundreds of keys per page, so 3 levels hold 100M+ keys. Linked leaves make range scans cheap.
Index on (a, b, c). Which queries can seek: a=1, b=2, a=1 AND b=2 ORDER BY c?
a=1 yes. b=2 no, the leading column is missing. a=1 AND b=2 ORDER BY c yes, with no sort step.
Does Postgres have a clustered primary key like InnoDB?
No. Postgres tables are heaps. Every index, including the PK, is secondary and points to the row by ctid (page, slot). InnoDB stores rows inside the PK B+tree and its secondary indexes store the PK value.
An index on a boolean column is ignored. Why is that correct?
Half the rows match. Fetching them one random page at a time costs more than one sequential pass over the table. Use a partial index if you query the rare value.
Why can WHERE lower(email) = ? be slow with an index on email?
The index is sorted by email, not lower(email). Create an expression index on lower(email), or store emails lowercased.
