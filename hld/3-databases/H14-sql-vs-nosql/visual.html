Nothing pushes you out of relational, so keep ACID, joins and constraints.

Say this in the interview

"I pick the store by access pattern, not hype. Default Postgres: ACID, joins, constraints, JSONB for flexible bits. I leave it for a specific reason: huge key-value traffic to DynamoDB or Redis, write volume beyond one cluster to Cassandra, a real graph to Neo4j, search to Elasticsearch fed by CDC."

"NoSQL scales out because self-contained records avoid cross-shard joins. The price is duplicated data and usually eventual consistency, so money stays in SQL."

Same query, two ways

-- relational: join at read time
SELECT u.name, o.*
FROM users u JOIN orders o
  ON o.user_id = u.id
WHERE u.id = 'u42';

// document: one self-contained read
db.users.findOne({ _id: 'u42' })
// { name, orders: [ {...}, {...} ] }

-- wide-column: one table per query
PRIMARY KEY ((chat_id, month), msg_id)
WITH CLUSTERING ORDER BY (msg_id DESC)

Check yourself

Why are joins the enemy of sharding?
After sharding, the rows a join needs live on different machines. The join becomes network hops and scatter-gather. Denormalised records put everything one read needs on one partition.
In step 5 the document store rewrote four copies. What is the general lesson?
Denormalising moves the cost from reads to writes. Every duplicated fact must be updated everywhere, with no foreign key to help, often asynchronously, so readers can see old and new values for a while.
Is "MongoDB is AP, Postgres is CP" correct?
Only roughly. MongoDB with majority write and read concerns behaves CP-like; a single Postgres node is not a distributed system at all. Talk about the configuration (replication mode, quorum), not the brand.
You need flexible product attributes but also orders with transactions. One DB or two?
Often one: Postgres with a JSONB column (GIN index) for attributes, normal tables for orders. You keep joins and ACID. Move to a document store only if scale or workflow really needs it.
