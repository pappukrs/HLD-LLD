Consistent Hashing

With hash(key) % N, changing N moves almost every key. Put servers and keys on one ring instead: adding or removing a server then moves only the keys in one arc. Virtual nodes make the load even, and the same ring gives you replica placement.

Say this in the interview

"With hash % N, going from 4 to 5 nodes remaps about 80% of keys, which is a miss storm on the database. I'll put nodes and keys on a hash ring and give each key to the first node clockwise, so a join or leave moves only about 1/N of the keys. Each node gets about 150 virtual nodes so the load stays even and a failure spreads across all survivors. Replicas go to the next 3 distinct physical nodes clockwise, in different AZs."

Where it's used

  • DynamoDB, Cassandra, Riak: token ring + vnodes, replicas on the next N nodes
  • Memcached clients (ketama), Redis client-side sharding
  • Nginx hash $key consistent, Envoy ring hash and Maglev: sticky routing that survives scaling
  • Not a ring, same goal: Redis Cluster (16,384 slots), Kafka partitions

Check yourself

A server dies. Where do its keys go?
To the next server clockwise. With virtual nodes, its many small arcs go to many different servers, so no single neighbour is flooded. Step 9 shows this.
Why can't two replicas just be "the next 2 points"?
The next point may be another vnode of the same physical server. Then both copies are on one machine. Skip vnodes of servers already chosen (and servers in an AZ already used).
Does consistent hashing fix a hot key?
No. One key always lands on one owner. Use a local cache, read from all replicas, or split the key into key#0..#9.
Is there anything simpler for a fixed shard count?
Yes. If you pre-split into, say, 1024 logical shards and only move shards between machines, % 1024 plus a shard → node map is enough. Jump consistent hash also works when shards only grow at the end.
