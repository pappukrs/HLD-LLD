Leader-Follower Replication

One leader takes all writes and streams its log to followers. Followers serve reads, so reads scale. With async replication followers lag behind, so a user can read old data, and a failover can lose acked writes. Switch to semi-sync to see the difference.

Say this in the interview

"Writes go to the primary; two replicas in other AZs serve reads. Lag is usually milliseconds but can spike to seconds, so for read-your-writes I return the commit LSN, keep it in the session, and read only from a replica that has replayed it, else the primary. Failover promotes the most up-to-date replica and bumps the term, so the old primary is fenced. For money I use semi-sync, so an acked write is on two machines. And replicas are not backups: we keep PITR."

Fixes for stale replica reads

  • Read-your-writes: after a write, read from the leader for ~10 s, or wait until a replica reaches the write's log position (LSN).
  • Monotonic reads: pin a user to one replica (hash of user id), so time never goes backwards for them.
  • Consistent prefix: keep related writes in one partition, so a reply never shows before its question.

Check yourself

A user edits their profile, refreshes, and sees the old name. Why, and how do you fix it?
The refresh hit a replica that had not applied the write yet. Fix with read-your-writes: route that user's reads to the leader for a short window, or carry the write's LSN in the session and pick a replica that has reached it.
What is split brain and how do you prevent it?
Two nodes both act as leader and accept writes, so data diverges. Prevent it with a majority-based election (Raft, etcd, ZooKeeper) and fencing: each leader gets a higher term, and followers or storage reject writes with an older term.
Does adding replicas help write throughput?
No. Every replica still applies every write, and all writes go through one leader. To scale writes you shard the data.
In semi-sync mode, why was write 44 not lost?
The leader waited for DB-2 to store entry 44 before acking. When the leader crashed, DB-2 had the highest log position, so it was promoted with 44 already in its log.
Why is a replica not a backup?
It replays every statement, including a bad UPDATE or DELETE, within milliseconds. Only backups with point-in-time recovery (or a delayed replica) let you go back in time.
