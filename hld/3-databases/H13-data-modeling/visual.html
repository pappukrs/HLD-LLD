Data modelling and normalization

One wide table stores the same fact many times, so a single change can leave the data disagreeing with itself. Watch a flat orders table break, then split it into 3NF tables joined by keys, and finally copy one value back on purpose.

Try it: what does one email change cost?

Say this in the interview

"Customer to order is 1:N, so orders.customer_id is a foreign key with an index on (customer_id, placed_at DESC). Orders to products is M:N, so I add order_items with primary key (order_id, product_id). Core tables are in 3NF, so each fact lives in one place."

"I denormalize on purpose in two places: unit_price is a snapshot of the price paid, and orders.total is cached in the same transaction. Any other copy gets a CDC sync path and I accept a few seconds of lag."

Final schema (key lines)

customers  (cust_id PK, name, email UNIQUE)
products   (product_id PK, name, price_paise)
orders     (order_id PK, cust_id FK → customers,
            total_paise, placed_at)
order_items(order_id FK, product_id FK, qty,
            unit_price_paise,          -- snapshot
            PRIMARY KEY (order_id, product_id))
INDEX orders (cust_id, placed_at DESC)

Normal forms and denormalization at a glance

Form / choiceRuleBroken byFix
1NFOne atomic value per cellitems = "Pen x2, Book x1"One row per order line
2NFNo column depends on part of a composite keyproduct_id → name, price; order_id → cust_idproducts, orders tables
3NFNo column depends on a non-key columnorder_id → cust_id → emailcustomers table
BCNFEvery determinant is a candidate keyteacher → course inside (student, course, teacher)Split out teacher → course
Snapshot copyFreeze a historical factInvoice joining to today's priceorder_items.unit_price
Derived copyCache a value for a hot readCopy with no sync planSame transaction, or CDC consumer + repair job

Check yourself

Key is (order_id, product_id) and product_name depends on product_id. Which form breaks?
2NF: a partial dependency on part of the composite key. Move name and price into products.
Why is email in the orders table a 3NF problem and not a 2NF one, once orders has a single-column key?
With key order_id there is no "part" of the key. But email depends on cust_id, a non-key column. That is a transitive dependency, so it breaks 3NF.
Is order_items.unit_price a denormalized copy of products.price?
No. It is the price paid at purchase, a different fact. It must not change when the catalog price changes, or old invoices would change too.
How do you store "a post has many tags, a tag has many posts"?
A junction table post_tags(post_id, tag_id) with a composite primary key, plus an index on (tag_id, post_id) for "posts with tag X". Never a comma list in one column.
