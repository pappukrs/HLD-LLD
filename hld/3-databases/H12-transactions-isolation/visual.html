Transactions, Isolation and Locking

Two transactions run at the same time. Each isolation level decides which bad interleavings are possible. Higher levels stop more anomalies but cost more locking, aborts and retries. Locks (FOR UPDATE) and version columns fix the hot spots without raising the level for everyone.

Say this in the interview

"Postgres defaults to Read Committed, which still allows lost updates and write skew. For a balance or stock counter I'll use an atomic UPDATE ... SET x = x - 1 WHERE x > 0, or SELECT ... FOR UPDATE, or a version column. For invariants across rows, like 'at least one doctor on call', I'll use SERIALIZABLE and retry on serialization errors."

How the database does it

  • Read Committed: each statement reads a fresh snapshot of committed data.
  • Repeatable Read: the whole transaction reads one snapshot taken at its first statement (MVCC in Postgres and MySQL).
  • Serializable: the result equals some one-at-a-time order. Done with locks (2PL, MySQL, SQL Server) or by tracking read/write conflicts and aborting (SSI, Postgres).
  • Postgres asks for READ UNCOMMITTED but gives Read Committed. Dirty reads never happen in Postgres.
  • Default level: Postgres, Oracle and SQL Server use Read Committed; MySQL InnoDB uses Repeatable Read.

Check yourself

Two users buy the last item at Read Committed. What can go wrong?
Both read stock = 1, both write stock = 0 and both get an order: a lost update and an oversell. Use UPDATE items SET stock = stock - 1 WHERE id = ? AND stock > 0 and check that one row changed.
Why doesn't Repeatable Read stop write skew?
Each transaction writes a different row, so there is no write-write conflict to detect. Each one checked the rule on its own snapshot, which was correct when taken. Only Serializable looks at the read-write dependencies between them.
What must the application do at SERIALIZABLE?
Catch serialization failures (SQLSTATE 40001) and retry the whole transaction. Keep transactions short so retries are cheap.
Is SELECT ... FOR UPDATE enough for write skew?
Only if every transaction locks the same rows it checks. If the rule is about rows that may not exist yet (phantoms, e.g. "no overlapping booking"), you need Serializable, a unique or exclusion constraint, or a lock on a parent row.
