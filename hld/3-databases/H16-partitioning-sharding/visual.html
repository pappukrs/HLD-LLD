Partitioning and sharding

Sharding splits one big table across many databases so writes and storage scale. The shard key and the rule (range, hash, fixed partitions, directory) decide which queries stay on one shard, which shard gets hot, and how much data moves when you add a node.

Say this in the interview

"I'll shard by merchant_id with a hash, because almost every query is scoped to one merchant and a payment stays on one shard. I won't shard by time, since all new writes would hit one shard. I'll hash into 1024 logical shards and map them to nodes, so adding a node moves whole logical shards. Hashing spreads keys, not traffic, so whales get a directory override and hot counters get salted."

Choosing a shard key

  • High cardinality: many distinct values (user_id, not country).
  • Even traffic, not only even data: watch celebrities, flash sales, whale tenants.
  • Carried by the main query: "all orders of a user" should hit one shard.
  • Keeps what changes together on one shard, so transactions stay local.
  • Never changes for a row: changing it means moving the row.

Check yourself

Why is hash(key) % N bad for resharding?
When N changes, most keys get a new shard: 3 → 4 nodes moves about 75% of the data. Use fixed logical partitions or consistent hashing so only about 1/(N+1) moves.
A chat app shards messages by message_id. What breaks?
Loading one conversation needs messages from every shard. Shard by conversation_id (plus a time bucket for huge chats) so one conversation lives on one shard.
Data is even but one shard is on fire. Why?
A hot key. Hashing spreads keys, not traffic. Cache it, add read replicas to that shard, salt a write-heavy key into sub-keys, or move the tenant to its own shard.
Local vs global secondary index?
Local: writes stay on one shard, reads by that field scatter to all shards. Global: reads hit one index shard, but each write also updates another shard, usually async.

Where it shows up

  • Chat: messages by (channel_id, time bucket) (Discord).
  • Payments: by merchant_id, whales on dedicated shards.
  • IoT telemetry: by device_id, not timestamp.
  • Redis Cluster: 16384 slots moved between nodes.
  • Instagram: thousands of logical Postgres shards on fewer servers.
