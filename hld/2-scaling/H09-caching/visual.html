Caching patterns, stampedes and penetration

A cache pattern answers two questions: who fills the cache on a read, and where a write goes first. Each choice trades freshness, write speed and the risk of losing data. A hot key that expires can flood the database, and keys that do not exist can bypass the cache entirely.

Try it: what does the hit rate buy you?

Say this in the interview

"I'll use cache-aside with Redis: read the cache, on a miss read the DB and set the key with a TTL. On a write I update the DB and then delete the key, so the next read refills it. For hot keys I protect the DB from a stampede with a short lock or single-flight, plus TTL jitter so many keys don't expire together."

Why delete, not update, on write?

Two writers can update the DB in one order and the cache in the other order. The cache then keeps the older value until the TTL ends. Deleting the key avoids this race: the next reader loads the current row.

A small race remains (a slow reader can put an old value back after the delete). The TTL bounds it. Some teams delete twice: now and again after ~1 s.

Check yourself

Which pattern for a bank balance? For a "likes" counter?
Balance: the DB is the source of truth; cache-aside with delete-on-write, or no cache for the write path. Likes: write-back is fine, because losing a few increments is acceptable and the write rate is high.
What causes a cache stampede, and three fixes?
A hot key expires and many requests miss at once, so all of them query the DB. Fixes: a lock or single-flight so only one request rebuilds; serve the stale value while one request refreshes; TTL jitter or early probabilistic refresh so keys don't expire together.
Single-flight in one Node process: is it enough?
It merges misses inside one process only. With 50 app instances you can still get 50 DB queries. Use a Redis lock (SET lock:key 1 NX PX 3000) for one rebuild across all instances.
