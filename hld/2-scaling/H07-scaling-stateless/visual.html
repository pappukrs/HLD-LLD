Scale up, scale out, and why servers must be stateless

A bigger box helps until it hits the ceiling or dies. More boxes help only if any box can serve any request. Watch a session get lost, then moved to Redis, then watch the bottleneck move to the database.

Say this in the interview

"Short term I can scale up, but there's a ceiling and it stays a single point of failure, so the plan is to scale out behind a load balancer. That needs stateless app servers: sessions in Redis or short-lived JWTs, files in S3, counters in Redis, cron behind a lock. Statelessness relocates state, so the new home must be more reliable than the server was. Scaling out moves the bottleneck to the database, so I'd add PgBouncer and cap autoscaling."

Check yourself

Why did request 2 get a 401?
The session lived in app1's memory. Round robin sent the next request to app2, which had never seen that session id.
Is sticky sessions a fix?
A shortcut. It pins a user to one server, so load gets uneven and the user is logged out when that server dies. Never make correctness depend on it.
You moved sessions to one Redis node. What's the new risk?
Redis is now a SPOF on every request. Give it a replica and automatic failover (Sentinel or cluster mode), and decide persistence and TTLs.
Why did the DB fail at 100 instances?
Each instance opens its own pool: 100 × 20 = 2,000 connections. Use a pooler like PgBouncer or RDS Proxy and cap the autoscaling max.
