Say this in the interview

"Static assets and media live in S3 behind a CDN. File names carry a content hash, so they are cached for a year with immutable and deploys never purge; only the HTML has a short s-maxage. Personal API responses are private, no-store. An origin shield and request collapsing turn a viral miss storm into one origin fetch. Paid videos use signed URLs that the edge verifies."

Which Cache-Control for what

ContentHeaderWhy
Hashed JS/CSS/imagespublic, max-age=31536000, immutableNew version = new URL, so caching forever is safe
HTML entry pagepublic, max-age=0, s-maxage=60, stale-while-revalidate=30CDN keeps it briefly; browsers always revalidate
Shared API data (catalog, scores)public, s-maxage=5..60Same for everyone; short freshness
User-specific API (/api/me, cart)private, no-storeNever in a shared cache
Paid video segmentspublic, max-age=86400 + signed URLCached at the edge, access checked by signature

Check yourself

Why did user B see user A's profile?
/api/me is the same URL for everyone. With a public header the edge cached A's response under that URL and served it to B. Personal responses must be private, no-store.
Why prefer hashed file names over purge?
A new version is a new URL, so nothing stale can be served, nothing needs purging, and you can cache for a year. A purge takes seconds to minutes and then every PoP misses at once.
What does the shield buy you?
Misses from many PoPs for the same object become one origin request. Without it, a viral object means one origin fetch per PoP, all at the same moment.
Does a CDN help an uncacheable API?
Yes. TLS ends at a nearby PoP and the edge reuses warm connections to the origin, saving long round trips on every new connection.
